# UI Shell Guide

## Overview

Trace Atlas's UI is a "Sleeve & Glass" tablet shell. `Tablet.tsx` composes two decorative `SleeveContainer`s flanking a single `ScreenViewport`:

```typescript
<SleeveContainer hasPowerSwitch={true} />
<ScreenViewport isPoweredOn={isPoweredOn} />
<SleeveContainer />
```

- `SleeveContainer` (`src/components/panels/physical/`) is purely decorative housing — a logo mark, and the `PowerRockerSwitch` when `hasPowerSwitch` is set. No interactive UI besides the power switch itself lives here.
- `ScreenViewport` (`src/components/panels/physical/`) is the actual interactive surface. When `isPoweredOn`, it renders `Header`, `WorldView`, `NavPanel`, `NavToggleButton`, and `ContentPane` (all under `src/components/panels/screen/`), in that order. `Header` is a sticky, always-visible bar that absorbed both the old `TransportBar`'s controls and `HubNav`'s tile-navigation buttons (`docs/specs/HEADER_HUB_CONSOLIDATION.md`), then lost its own navigation entirely a second time to the nav tree described below (`docs/specs/NAV_LAYOUT_REWRITE.md` Task 10). Its volume slider briefly relocated to Settings → Volume only (Task 11) and was moved back per a follow-up call — volume should always be reachable, not gated behind a nav selection — so it's now bound to the same `audioStore.volume` in both places. What's left: a master volume `SliderLinear`, a Mute `Toggle` (an icon facade, 🔇/🔊 swapped on `isMuted`, replacing the old stacked-text facade — Mute stays regardless of which Settings leaf is open, so it never moved), and a status block showing the current Attenuation Style's locale coordinates plus a `HH:MM -XX°C` local-time-plus-decorative-temperature reading (purely cosmetic — no gameplay effect). `Header` has no restart or pause/play controls; BPM lives at Settings → Tempo, not read out here. **Known-stale mechanism, not cleaned up:** `useHeaderRowFit`/the `header--inline` class it drives are still wired up in `Header.tsx` and still measured live, but no CSS rule targets `.header--inline` anymore since an earlier restyle replaced that row-merge approach with hand-authored breakpoints — currently a dead, if harmless, measurement. `RobotList` was removed in Roadmap Phase 2 (Layout) — Phase 8's Robot Selection tile replaces it.

**Guardrail** (see [CLAUDE.md](../CLAUDE.md)): all interactive UI — transport, navigation, controls — lives inside `ScreenViewport` only, never in `SleeveContainer`.

## Console Navigation

**As shipped** (`docs/specs/NAV_LAYOUT_REWRITE.md`, `docs/tasks/NAV_LAYOUT_REWRITE.md` — both read for full design rationale/history; this section describes the result, not the plan). The old flat 3-tile model (`Header`'s `RadioButton` nav group, `src/data/headerNavConfig.ts`) is gone entirely — `headerNavConfig.ts` is deleted, and `Header` carries no navigation at all anymore (see the Overview section above). Navigation is a schema-driven, hand-rolled ARIA tree: `NavTree`/`NavPanel`/`NavToggleButton`/`ContentPane` (`src/components/panels/screen/nav/`, `src/components/panels/screen/console/ContentPane.tsx`, schema in `src/data/navTreeConfig.ts`). `HubNav` (`docs/specs/HEADER_HUB_CONSOLIDATION.md`) and the `ConsoleNavigation` `Tabs.Root` bar before it are both historical — this is the tree model's third replacement in the app's history, not the second.

**Shell composition** (`ScreenViewport.tsx`): `NavPanel` renders `NavTree` inside a shell that's permanently docked on the left on desktop/tablet, and an off-canvas slide-over on mobile (`useCabinetTier`'s existing breakpoint tiers — no new breakpoint invented), animated via a `timelineMap`-registered GSAP timeline (`prefers-reduced-motion` respected). `NavToggleButton` (a hamburger/✕ button) renders only on the mobile tier, reachable regardless of what `ContentPane` shows. Selecting any node closes the mobile panel automatically (never on desktop/tablet, where it's always open). `NavPanel` also carries a "Home" button above `NavTree` (relocated from `ContentPane`'s own former "Close" button, same reset behavior — clears `activeHubTile` and every entity/section field a branch could have set) so it's always reachable, not only once a tile is active. `ContentPane` (repurposed from the old `Console.tsx`, same "render nothing when nothing's selected" contract) is the single area a selection opens into — still delegates to `ConsolePanel`'s `TILE_CONTENT: Record<HubTile, ...>` dispatch internally, keyed on `uiStore.activeHubTile`; at the blank/landing state it instead renders a small `Textbox` welcome card (`.content-pane__home`, sized to its own content, not full-bleed — a full overlay there would block `Robot.tsx`'s own click-to-select handling, which depends on nothing blocking `WorldView` at that state).

**`NavBreadcrumb`** (`src/components/panels/screen/nav/NavBreadcrumb.tsx`) is a separate, passive "where am I" readout living outside the nav tree entirely — full-width along the bottom on mobile, bottom-left once docked (desktop/tablet), reusing `NavPanel`'s own `useIsNavPanelSlideAway` breakpoint rather than inventing a new one. It reads `useNavTree()`'s `selectedPath` (see below) and renders nothing at the true blank/landing state. Read-only by design — no click-to-navigate; `NavPanel`'s own "Home" button already covers jumping back to the top.

**Content model** (`docs/specs/NAV_PANEL_VIEWS_AND_CONTENT.md`, superseding the original Nav & Layout Rewrite's swap-model this section used to describe — both specs are read for full design rationale/history): each of the 4 branches' content components no longer render exactly one selected leaf's content and nothing else. Instead, each renders **one continuous scrollable view** stacking every section for the current context (the whole branch for Settings/Fleet Params; the selected robot, "All Probes," or selected company for Probes/Companies), with each section wrapped in an `AccordionContainer` — restored from git history and converted from an uncontrolled `defaultOpen` component to a controlled `open`/`onOpenChange` one for this pass (see `COMPONENT_LIBRARY.md`).

**Accordion open/closed state is manual and independent per section** (`useAccordionOpenState`, `src/components/panels/screen/nav/`) — each accordion tracks its own state; opening one never closes another (except the mobile nav-click sibling-closing described below), and multiple can be open at once. This reverses the pass's own original design (a single derived-open accordion, view-wide, computed from `selectedSettingsLeaf`/`selectedFleetParamsEffect`/`selectedSection`+`selectedSubsection`) per Crawford's follow-up call, 2026-09-24: nav clicks and scrollspy should never auto-open or auto-close an accordion by themselves — a later pass (below) reopened exactly one door back in, by nav click alone, deliberately, not by reversing that call. Each view opens exactly one section by default on mount (its first leaf in tree order) — `useAccordionOpenState`'s `defaultOpenId` — and, for `RobotOptionsTab`/`CompanyOptionsSection`, resets back to that default whenever the entity changes (`resetKey`: the robot's id, or the company/"All Probes" prefix) — switching robots or companies doesn't carry over which accordions were left open on the last one.

**Nav ↔ accordion sync** (`docs/specs/NAV_ACCORDION_SYNC.md`, `docs/tasks/NAV_ACCORDION_SYNC.md`) — `src/utils/accordionSync.ts` is a live mirror of every `useAccordionOpenState` instance's open/closed state, keyed by the same node ids the tree and `sectionRefs.ts` already use (accordion ids and nav-tree ids are the same string, e.g. `probes.r1.melody.rhythm`). It exports `registerAccordion`/`unregisterAccordion` (write side, called by `useAccordionOpenState` on mount/`setOpen`/`openExclusive`/unmount/`resetKey` reset), `isAccordionOpen`/`subscribeAccordionOpen` (read side, called by `NavCabinetRow` via `useSyncExternalStore`), and `openAccordionFromNav` (write side, called by nav clicks). It is a mirror, never the source of truth — each view's own `useAccordionOpenState` remains authoritative. It serves both directions:
- **Nav → content:** a nav click (`NavTreeNode.tsx`) calls `openAccordionFromNav(node.id, { closeSiblings })` right alongside `select`/`scrollToSection`, opening that id's accordion if one is registered — a safe no-op otherwise (e.g. the "Pitches" leaf, whose content was merged into the "Composition"/`.rhythm` accordion and has no anchor of its own). `closeSiblings` is `true` only on the mobile tier (`useCabinetTier() === 'mobile'`, the same shared breakpoint hook `ScreenViewport`'s own docked/off-canvas nav split already uses) and only closes other ids within the *same* `useAccordionOpenState` instance — never across views, never on tablet/desktop.
- **Content → nav:** opening an accordion (`useAccordionOpenState.setOpen`/`openExclusive`, from any source — a nav click or the accordion's own header) also calls `expandNavAncestorsForId` (extracted out of `useNavTree.ts`'s own `select()`, which still calls the same function) so the branch/entity-level nav ancestors expand even if the accordion was never reached via a nav click. `NavCabinetRow.tsx`'s pop state (the deepest 2 tree levels' own chrome) subscribes to the registry via `useSyncExternalStore`, popping whenever its id's accordion is open, independent of its existing hover/focus/press conditions. **Closing** an accordion only reverts the pop signal — it never calls into `expandedTopLevelBranch`/`expandedProbeId`/`expandedCompanyId` or `selectedSection`/`selectedSubsection`, so collapsing a section never collapses the nav tree.

**Click-to-scroll:** clicking a top-level branch node jumps to the top of that view; clicking anything deeper scrolls to that item's own section position, then opens that item's accordion per the nav→content sync above. The scroll itself is an instant `scrollIntoView` jump (`src/utils/sectionRefs.ts`'s `scrollToSection`), never GSAP-animated — it isn't animation, so CLAUDE.md's GSAP-for-animation rule doesn't apply. Each section registers its own DOM anchor in `sectionRefs.ts` (a `Map<string, HTMLElement>` keyed by the same node ids the tree uses, mirroring `setRef`/`getRef`'s shape but scoped to content-pane anchors instead of top-level SVG refs) via a plain ref callback — `NavTreeNode`'s own click handler calls `scrollToSection(node.id)` right alongside `select(node.id)`, a no-op for any section that hasn't mounted an anchor yet. `select(node.id)` still updates `selectedSettingsLeaf`/`selectedFleetParamsEffect`/`selectedSection`+`selectedSubsection`, purely for tree row highlighting (`useNavTree`'s `isSelected`) — those fields have no bearing on any accordion's open state.

**Scrollspy and lazy-mount** share one `IntersectionObserver` per view (`src/components/panels/screen/nav/useSectionObserver.ts`): as the user manually scrolls (not via a nav click), whichever section comes closest to the top of the viewport drives the same selection-state update a click would (tree highlighting only, never an accordion's open state), without ever calling `scrollToSection` — a scroll-driven update must never fight the user's own scroll. The same observer doubles as the lazy-mount gate formerly owned by `AccordionContainer` itself (`ACCORDION_LAZY_MOUNT.md`'s "mount once, stay mounted" contract) — a section's real content only constructs once its anchor first nears the viewport, then stays mounted for the rest of that robot's/company's session even if scrolled away or collapsed again, matching pre-Task-21 `AccordionContainer` behavior but retriggered by scroll proximity instead of a click. Lazy-mount is otherwise independent of open/closed state — a section's content can be mounted while its accordion is visually collapsed.

**Section/subsection shape is now one shared table, not hand-duplicated per view** (`docs/specs/ROBOT_SECTION_CONFIG_CONSOLIDATION.md`): `ROBOT_SECTIONS_CONFIG` (`src/data/robotSubsectionConfig.ts`) is the single source for every Probes/Companies section's and subsection's id, nav-tree label, accordion-trigger label, trait, and nesting shape (only `source` wraps its subsections in its own accordion; `melody`'s `frequency`/"Pitches" subsection has no accordion of its own, merged into `rhythm`'s "Composition" accordion instead). `useNavTree.ts` reads it to build the Probes/Companies nav-tree nodes; `RobotOptionsTab`/`CompanyOptionsSection` both render through a shared component, `RobotSectionAccordionStack` (`src/components/panels/screen/nav/RobotSectionAccordionStack.tsx`), that maps the same table into the accordion/anchor shell — each of those two content components supplies only its own value derivation and action wiring via a `renderSubsection` callback, never its own copy of the accordion ids/labels/nesting. This replaced 3 independently-hand-typed copies of the same id/label table (`useNavTree.ts`'s own `SECTION_CHILDREN`/`SUBSECTION_CHILDREN`, plus the inline `AccordionSchema` literals each of `RobotOptionsTab.tsx`/`CompanyOptionsSection.tsx` used to author). Settings/Fleet Params are unaffected — see `COMPONENT_LIBRARY.md`'s `AccordionContainer` entry.

**Probes/Companies gained a 4th tree level** (`RobotSubsection` — `audioSettings`; `rhythm`/`frequency`; `pingContour`; `baselineOscillator`/`coaxialOscillator`/`harmonicOscillator`; `probeDrift`) so each of their 5 sections' own children are individually addressable, matching Fleet Params' existing 3-level depth — node ids grow one segment (`probes.<id>.<section>.<subsection>`). "Volume" renders as "Output" — a label-only rename; every internal identifier (`RobotSection`'s `'volume'` value, `globalAudio.lfoDrift.robots`) is unchanged. `RobotDriftPanel` originally rendered as Source's 4th nested child ("Probe Drift"); it was later split out into its own top-level `RobotSection` (`'probeDrift'`, single accordion, no `ownAccordionLabel` — same shape as `volume`/`melody`/`envelope`), sibling to Source rather than nested inside it, at Crawford's own request. `PingControlsDrawer`/`SignatureArrayDrawer` each split into independently-mountable pieces to match this granularity (`PingControlsRhythmSection`/`PingControlsFrequencySection`, and `SignatureArrayLayer`/`RobotDriftPanel` exported standalone) — their old combined-drawer exports still exist, but nothing renders them anymore. `RobotOptionsTab`/`CompanyOptionsSection` each replaced their old `switch (section)` with the stacked-accordion model above, `CompanyOptionsSection` additionally losing its old `section` prop (it now reads `selectedSection`/`selectedSubsection` from `uiStore` directly, like `RobotOptionsTab`).

**Ancestor auto-expand:** selecting any node (a click, or a scrollspy-driven sync) also expands every tree row needed to reveal it — `expandedTopLevelBranch` always, plus `expandedProbeId`/`expandedProbeSection` or `expandedCompanyId`/`expandedCompanySection` for Probes/Companies, `expandedFleetParamsGroup` for Fleet Params — so the highlighted row is never hidden inside a collapsed ancestor.

---

**The tree itself** implements the full WAI-ARIA APG Tree View pattern by hand (no Radix primitive covers it): `role="tree"`/`role="treeitem"`, `aria-expanded`, `aria-selected`, roving `tabindex` (one node at `tabindex="0"`, everything else `-1`), Up/Down/Left/Right/Enter/Space keyboard support. Each row (`NavTreeNode.tsx`) has two independent controls — clicking the name **selects** it; clicking a separate `+`/`−` button (rendered only when the node has children) **toggles expansion only**, `stopPropagation`'d so it never also selects. Selection and expansion are fully decoupled state: you can peek open a branch without navigating into it, and selecting a node doesn't force its parent open or closed. Expansion is "accordion-of-one" *per level* — expanding one node collapses its previously-expanded sibling at that same level, tracked by a small set of purpose-specific `uiStore` fields (one per level: `expandedTopLevelBranch`, `expandedProbeId`, `expandedCompanyId`, `expandedFleetParamsGroup`), not one generic node-id scheme — deliberately additive rather than a parallel selection-state representation of the tree.

**`useNavTree()`** (`src/components/panels/screen/nav/useNavTree.ts`) is the one place a node's generic string id (`<branch>[.<entityId>[.<section>[.<subsection>]]]`, e.g. `probes.r4.volume.audioSettings`, `companies.c2`, `fleetParams.eqFilters.eq`) is ever parsed — every other component (`NavTreeNode`, `ContentPane`'s content components) reads only its typed `isSelected`/`isExpanded`/`select`/`toggleExpand`, never the id itself. It also merges `navTreeConfig.ts`'s static schema with the two dynamic subtrees — one `probes.<robotId>` node per robot and one `companies.<companyId>` node per company in the active locale, both regenerated live (no remount) as the roster/company list changes. Probes/Companies gained a 4th level (`RobotSubsection`) under `docs/specs/NAV_PANEL_VIEWS_AND_CONTENT.md` — see that pass's own section above for what changed and why.

It also returns `selectedPath` — the root-to-node ancestor chain of whichever node currently satisfies `isSelected` (a depth-first search, since `isSelected` only answers one id at a time and has no separate "what's currently selected" value of its own), `[]` when nothing is selected. Built for `NavBreadcrumb` (see above), kept here rather than re-derived elsewhere so id-parsing stays centralized. Defensively keeps the *deepest* match if more than one id ever reads `isSelected() === true` at once — `isSelected`'s own comments already document one such gap (`selectedFleetParamsEffect === null` matching both a bare branch and a bare category node simultaneously). Finding this also caught a real, pre-existing bug: `FLEET_PARAMS_LEAF_TO_EFFECT_KEY` was missing `frequency`/`duration` entries, so selecting Pacing's own Frequency/Duration leaves silently set `selectedFleetParamsEffect` to `null` instead of `swellFrequency`/`swellDuration` — fixed alongside `selectedPath`'s own addition.

`selectedPath` is then trimmed of a trailing *childless* node (`trimToLowestParent`) before being returned — Crawford's own follow-up call: the breadcrumb should read as "the lowest-level PARENT the user is under," not the exact selected leaf. A specific field (Fleet Params' "Reverb", a robot's "Rhythm" subsection) is dropped in favor of the group/section that houses it ("Time & Space", "Composition") — matching where the accordion boundary actually sits. A node that itself has children (a bare branch, a robot/company entity, a Fleet Params/Settings category, a section with its own subsections) is never dropped, so `"Companies"` and `"Probes / Unit One"` stay whole.

**`uiStore`'s nav-specific fields** (all plain JSON-serializable primitives, see the `uiStore` section below for the full list) exist because the tree deliberately has no single opaque "selected node id" — each level of "which thing is open/selected" gets its own small, typed field, added incrementally as each branch's real content was built out, rather than one generic scheme parsed everywhere.

**`AccordionContainer`'s own history** — retired once the Nav & Layout Rewrite's leaf-per-node model made every one of its consumers (`AudioRigDrawer`, `PingControlsDrawer`, `PingContourDrawer`, `SignatureArrayDrawer`, `AudioSettingSection`) redundant (`docs/specs/NAV_LAYOUT_REWRITE.md` Task 21), then restored and made controlled once the view/accordion/scroll model above needed it again (`docs/specs/NAV_PANEL_VIEWS_AND_CONTENT.md` Tasks 3-4) — see [COMPONENT_LIBRARY.md](COMPONENT_LIBRARY.md) for the full history and its new controlled contract.

**Robot Systems Engine (Phase 7) / Robot Selection (Phase 8) / Robot Options (Phase 9), unaffected by this rewrite:** the roster is fixed at exactly 12 robots created once per locale (no dynamic spawn/despawn — see [ROBOT_LIFECYCLE.md](ROBOT_LIFECYCLE.md)); `RobotsTab` renders one `RobotSelectionCard` per robot (avatar, job, battery, docking, an `AudioStatusBadge` colored dot); selecting one shows `RobotDisplaySection`/the 4 drawers as described in the Probes row above, all schema-driven from `src/data/robotOptionsConfig.ts` and live-wired to `AudioEngine`/`useLocaleStore`. See [COMPANIES.md](COMPANIES.md) for the Companies domain model (Phase 10) that the Companies branch above now edits through the tree instead of the old button-row UI.

## uiStore

UI-only, JSON-serializable state (`src/stores/uiStore.ts`): `activeView`, `theme`, `language`, `isPoweredOn`, `isFullscreen`, `activeLocaleLocalTime`, `activeLocaleTemperature` (`docs/specs/HEADER_HUB_CONSOLIDATION.md` — same shape/placement/no-persistence convention as `activeLocaleLocalTime`, purely decorative, read by nothing but `Header`), `selectedRobotId`, `selectedCompanyId` (Phase 10 — independent of `selectedRobotId`), `allRobotsSelected` (the Robots tab's own "All" company-filter default, mutually exclusive with `selectedCompanyId` — a different concern from `allProbesSelected` below despite the similar name), `activeHubTile`.

**Nav & Layout Rewrite additions** (`docs/specs/NAV_LAYOUT_REWRITE.md` §1.3, plus a few more added as real content gaps were found during implementation — see "Console Navigation" above): `selectedSection` (`RobotSection | null` — which of a robot/company/All-Probes' 5 sections, Output/Melody/Envelope/Source/Probe Drift, is open), `isNavPanelOpen` (mobile only), `expandedProbeId`/`expandedCompanyId`/`expandedFleetParamsGroup`/`expandedTopLevelBranch` (one accordion-of-one field per tree level), `selectedSettingsLeaf` (Settings isn't an "entity" the way a robot/company is, so it needed its own field rather than reusing `selectedSection`), `selectedFleetParamsEffect` (reuses `AudioRigEffectKey` directly rather than a parallel string union), `allProbesSelected` (disambiguates the bare "Probes" browse node from the "All Probes" bulk-edit leaf — both otherwise read `selectedRobotId === null` with no other signal). `clearSelectedCompany` resets `selectedCompanyId` alone, without touching `allRobotsSelected` — used when navigating to the bare "Companies" node, a different concern than `selectAllRobots`.

**`NAV_PANEL_VIEWS_AND_CONTENT.md` additions** (the 4th tree level and the stacked-view/accordion model above): `selectedSubsection` (`RobotSubsection | null` — the open great-grandchild within a `selectedSection`, e.g. `'rhythm'` within Melody; `null` means that section's own first subsection acts as the open one), `expandedProbeSection`/`expandedCompanySection` (one level deeper than `expandedProbeId`/`expandedCompanyId` — which section, if any, has its own children expanded in the tree within whichever probe/company is itself expanded). All plain strings/`null`, same as every other field here — no Tone nodes, GSAP timelines, or DOM refs (scroll anchors live in `sectionRefs.ts` instead, a parallel registry outside the store — see "Content model" above).

## Radix Primitives in Use

Installed and in use: `react-alert-dialog`, `react-dialog`, `react-dropdown-menu`, `react-popover`, `react-select`, `react-separator`, `react-slider`, `react-switch`, `react-tabs`, `react-toggle`, `react-toggle-group`, `react-toolbar`, `react-tooltip`, `react-visually-hidden`. Radix owns ARIA roles, focus trapping, and keyboard contracts; project design tokens own visual styling — don't install `@radix-ui/themes`.

## Forbidden Patterns

- Rendering any interactive control (buttons, inputs, nav) inside `SleeveContainer`.
- Storing GSAP timelines, DOM refs, or computed UI props in `uiStore` — only plain, serializable UI state.
