# Intent: World Clock — Deterministic Lifecycle Replay

Confirmed via `interview-me` on 2026-09-28, ahead of a `spec-driven-development` pass. Grounded in an earlier `/idea-refine` session (see [docs/ideas/world-clock-deterministic-lifecycle-replay.md](../ideas/world-clock-deterministic-lifecycle-replay.md), if saved) and roadmap [Phase 20.5](../todo/roadmap.md#205-world-clock-deterministic-lifecycle-replay). **Revised 2026-09-28, same day** — the first version of this doc scoped melody drift out ("melody itself... untouched by this phase"); a second interview pass expanded that after discovering the current code entangles dock-triggered melody pitch drift with the battery/docking state machine. See "What changed from the first pass" below.

## Outcome

Robot battery/docking/job *and* dock-triggered melody pitch drift (`docs/ROBOT_LIFECYCLE.md`) become a deterministic function of `(seed-derived spawn state, elapsed measures since roster creation)`, the same way melody's own *base* generation already is (roadmap Phase 31) — provable headlessly, with a new `Locale.createdAtMeasure` field and a pure, callable-outside-BeatClock replay function extracted from `robotSystems.ts`'s tick logic. Ships complete this pass — not just an audit — even though no consumer (Session Storage, Phase 21's share links, Phase 32's scrubber) wires it in yet. On-screen position/movement stays explicitly out of scope — confirmed intentional (see Out of scope), not a gap.

## Behavior

- **`Locale.createdAtMeasure: number`** — stamped once, at the same point `dayStartTimestamp` is (`buildLocale`/`initializeLocale`), reading `getCurrentMeasure()` at that moment. Elapsed measures for replay purposes is always `getCurrentMeasure() - locale.createdAtMeasure`, never a separately-tracked running total.
- **Replay always fully re-simulates from the locale's creation measure forward — never resumes from a mid-simulation checkpoint.** This is the mechanism that makes dock-triggered melody drift replayable for free: the per-robot dock-cycle count that seeds each pitch reroll (today, a live-only module-scope counter, `dockCycleCounters` in `robotSystems.ts`) falls out of the replay loop naturally, by counting `Departing`→`Docked` landings in chronological order as replay steps forward — no new persisted state needed beyond `createdAtMeasure` itself.
- **A pure, headless lifecycle-replay function**, extracted from `robotSystems.ts`'s existing tick step (battery drain/recharge, `Docked`/`Docking`/`Active`/`Departing` threshold transitions, `assignJob`/`scoreJobAffinities`) — same category of extraction as Phase 31's `buildSeededComposition` was for melody's base generation. Given a roster's seeded spawn state and a target elapsed-measures count, it replays every intervening measure in a tight loop with zero BeatClock subscription and zero AudioEngine/GSAP side effects, and produces the same per-robot `batteryLevel`/`docking`/`job` end state a real measure-by-measure run would have produced.
- **Melody pitch drift replays too, threaded through the same loop.** Each time the replay detects a `Departing`→`Docked` landing for a robot, it applies the same deterministic pitch-reroll step `reRollMelodyPitches` applies live (seeded by that robot's own dock-cycle count and the locale's noise map) — cumulatively, in the same chronological sequence a real run would have produced, since a robot's Nth drift operates on the result of its (N-1)th. `reRollMelodyPitches` itself, and Phase 31's underlying melody *base* generation, are unchanged — this only extends to the drift layer sitting on top of them.
- **The cross-robot "never zero Active robots" invariant must replay identically.** This is the one piece of the existing tick logic that reads joint 12-robot state each measure (a departure this same tick, re-read fresh, can block another robot's transition) — the replay function must reproduce this exactly, not approximate it, since it's the one place the tick logic isn't simple per-robot arithmetic.
- **No wall-clock/real-time dependency anywhere in the replayed path.** Confirmed already true for battery/docking/job by direct code reading: `robotSystems.ts`'s tick path has zero `Math.random` calls, `spawnInitialRoster` already seeds starting `batteryLevel`/`docking` deterministically from the noise map, and battery drain is a flat per-measure rate (`BATTERY_DRAIN_BASE` + a job-type surcharge) with **no dependency on movement, distance traveled, or position** — verified directly (the only place `batteryLevel` is ever written is `robotSystems.ts`'s tick; `idleSystem.ts` only *reads* it, one-way, to bias wander-destination Y-range).

## Style / constraint

- **Verification is a headless prove-it test, not a manual browser check.** No live UI consumes this yet (deliberately, see Out of scope) — a test asserting N real BeatClock-driven ticks and one headless replay call converge on identical end state (battery/docking/job *and* melody), across all 12 robots including the invariant case, is the acceptance bar. Same category as `types/session.ts`'s "the type-check is the verification" — here it's "the prove-it test is the verification."
- **Reuses the existing tick logic's and melody-drift logic's own rules** (`BATTERY_DRAIN_BASE`, `JOB_BATTERY_DRAIN_SURCHARGE`, `BATTERY_FULL_THRESHOLD`/`BATTERY_CRITICAL_THRESHOLD`, hold-measure durations, `scoreJobAffinities`, `reRollMelodyPitches`/`DOCKED_PITCH_DRIFT_RATIO`) via extraction, not a reimplementation — a second, parallel copy of any of this logic drifting from the real tick over time is the specific failure mode to avoid.
- **A short audit pass, non-blocking.** Before or alongside the replay build (not gating it — battery/docking/job/melody-drift's own determinism is already independently confirmed), trace every other timing-dependent system (LFO drift, audio swells, ping-variance automation) and record, in a short findings doc, which are already measure-quantized and safe per `CLAUDE.md`'s existing no-`setInterval`-for-musical-timing guardrail, and which aren't. Informational for future phases, not a requirement this phase's own deliverable depends on.

## Out of scope

- **On-screen position/movement — confirmed intentional, not a gap.** `handleRobotIdle`'s continuous animated wandering (`idleSystem.ts`) is fundamentally not measure-snapshot state the way battery/docking/job are — there's no "position at elapsed measure N" to replay *to*. The one real coupling (battery level biases wander-destination Y-range, `idleSystem.ts:130`) is one-way and purely visual; it doesn't affect anything this phase replays, and doesn't need to be "untied" in code. A `Docked` robot's own dock-cycle position (`generateSpawnPosition`) also stays unreproduced by replay — it's off-viewBox/invisible while docked regardless.
- Wiring `createdAtMeasure`/the replay function into `SessionPayload`, Phase 21's share links, or Phase 32's scrubber UI — downstream consumers, once each is ready to use it.
- Fixing anything the audit surfaces beyond battery/docking/job/melody-drift — likely its own follow-up phase(s), not snowballed into this one.
- A "checkpointed replay" performance optimization (memoizing lifecycle state every N measures) — stays a fallback; not built unless a real perf check at realistic elapsed-measure counts says it's needed. Directly in tension with "always replay from creation," so only worth revisiting if that assumption turns out to be too slow in practice.
- Any dev-only debug hook/manual-trigger UI to exercise the replay by hand — the headless test is the proof; manufacturing something to click would be scope creep against the no-live-consumer constraint above.
- Melody's *base* generation formula (Phase 31) — unchanged; this phase only extends to the drift layer applied on top of it at each dock cycle.

## What changed from the first pass

The first version of this doc excluded melody entirely ("melody itself... untouched by this phase"), reasoning that battery/docking/job were the only state that drifts with elapsed time. Writing the spec against the real code (`docs/specs/WORLD_CLOCK_DETERMINISTIC_LIFECYCLE_REPLAY.md`, since being revised alongside this doc) surfaced that dock-triggered melody pitch drift (`reRollMelodyPitches`, called from `landOnDocked`) is itself dock-cycle-seeded and cumulative — the same kind of state as battery/docking/job, just currently entangled with a live-only counter. A second `interview-me` pass confirmed: bring melody drift into scope (it's the audible part of "share exactly what you're hearing," the phase's whole motivation), and explicitly rule position/movement out (it was never a snapshot-style value to begin with, and the one real battery↔movement coupling found (`idleSystem.ts`'s Y-range bias) turned out to need no code change at all — it's one-way and irrelevant to replay).

- Exact `Locale.createdAtMeasure` stamping point relative to `dayStartTimestamp` in `buildLocale` — almost certainly the same call site, but confirm against the final `types/locale.ts`/`worldTransition.ts` shape during the spec pass rather than assuming.
