## Core Audio Rules

The audio system is intentionally narrow: one shared `AudioEngine`, one transport-driven clock, and serializable robot descriptors.

- Initialize audio only from an explicit user gesture with `AudioEngine.start()`/`Tone.start()`.
- Treat the transport-backed BeatClock path as the authoritative clock for musical time; use `BeatClock` and `AudioEngine` for musical scheduling and avoid timers for music-aligned work.
- Use the shared `MIN_LEAD` (default `0.1s`) so notes are prepared ahead of playback.
- Keep voice creation, polyphony enforcement, and note scheduling inside `AudioEngine`; never create Tone objects in components or hooks.
- Keep only serializable data in Zustand state; store runtime-only objects such as voices, synth instances, and timelines outside state.
- Keep melodies index-based so harmony updates can change the pitch palette without regenerating the melody itself.

### AudioEngine API

`AudioEngine` is a plain object (no class). The methods below are the full export surface — roughly half of these were previously undocumented.

```typescript
export const AudioEngine = {
  // Lifecycle
  start: async (): Promise<void>,       // idempotent — no-ops if already initialized
  stop: () => void,                     // stops transport, clears playback tick; does NOT reset position or beat clock
  killAll: () => void,                  // full reset: cancels transport, resets position/counters, calls resetBeatClock()
  pause: () => void,
  resume: () => void,
  setBPM: (bpm: number) => void,        // no-op if not initialized; instant transport.bpm.value assignment, deliberately not ramped — see "BPM / Tempo" below
  now: () => number,

  // Scheduling
  scheduleNote: (params: { robotId: string; note: string; duration: NoteDuration | number; time?: number; velocity?: number; accentMultiplier?: number; position?: number }) => void,  // duration: a note value, or seconds for a rested/clipped note; position: the tick the velocity roll keys off (Robot Performance)

  // Voice management
  reserveVoice: (robotId: string, descriptor: OscillatorLayer[] | { base?: WaveformType; layers?: OscillatorLayer[] }, adsr: ADSREnvelope, phase?: number, detune?: number, pulseWidth?: number, masterVolume?: number, filterFreq?: number, articulation?: { portamento?: number; filterQ?: number; filterType?: RobotFilterType }) => boolean,  // filterFreq = the robot's bus filter cutoff (Hz); 0 = fully open; omitted = legacy fixed 1,200 Hz. articulation = glide seconds plus the bus filter's Q and type; absent = no glide, Q 1, lowpass
  releaseVoice: (robotId: string) => void,
  reReserveVoice: (robotId: string) => boolean,
  updateVoiceLayerParams: (robotId: string, layers: OscillatorLayer[]) => void,
  updateVoiceEnvelope: (robotId: string, adsr: ADSREnvelope) => void,  // the envelope carries the optional attackCurve / releaseCurve too
  updateVoicePortamento: (robotId: string, seconds: number) => void,  // live glide on every audible layer; 0 = none
  updateRobotBusFilter: (robotId: string, patch: { frequency?: number; Q?: number; type?: RobotFilterType }) => void,  // live bus filter edit; frequency and Q ramp over FILTER_RAMP_SECONDS
  updateRobotSends: (robotId: string, sends: Partial<Record<SendEngineKey, number>>) => void,  // a robot's five send gains into the shared rooms (Reverb, Delay, Colour, Shimmer, Double), keyed reverb / delay / grit / shimmer / double (SendEngineKey, src/data/robotSends.ts); writes only the keys given; also moves the robot in or out of each effect room's feeder set; 0..1, clamped, ramped over SEND_RAMP_SECONDS (0.05 s); a safe no-op with a devWarn when the robot is not reserved
  createCompositeVoice: (descriptor: OscillatorLayer[] | { base?: WaveformType; layers?: OscillatorLayer[] }, adsr: ADSREnvelope, portamento?: number) => CompositeVoice,
  getVoiceForRobot: (robotId?: string) => CompositeVoice | null,

  // Melody registry
  registerRobotMelody: (robotId: string, melody: MelodyEvent[]) => void,  // `melody` is superseded by the fixed Click Track pattern while the robot's `clickTrackActive` is true — see MELODY_SYSTEM.md's Click Track note
  unregisterRobotMelody: (robotId: string) => void,
  getRegisteredMelody: (robotId: string) => MelodyEvent[],   // test helper
  processMelodyStep: (currentStep: number, time: number) => void, // test helper
  getPolyphonyStats: () => { voices: number; maxVoices: number; step: number },

  // Global FX control (all no-ops if the underlying Tone node wasn't constructed, e.g. headless tests)
  setMasterVolume: (volume: number) => void,   // clamped [0,1]
  getMasterVolume: () => number,
  setGlobalReverb: (params: Partial<ReverbSettings>) => void,  // `wet` is the room's RETURN level (the room itself is always fully wet) and is immediate; `decay`/`preDelay` are coalesced (REVERB_IR_COALESCE_MS, 120 ms) and written only if changed, because each one makes Tone.Reverb re-render its impulse response
  setGlobalDelay: (params: Partial<DelaySettings>) => void,   // `wet` likewise drives the Delay room's return level
  setGlobalFilterLPF: (params: Partial<FilterSettings>) => void,
  setGlobalFilterHPF: (params: Partial<FilterSettings>) => void,
  setGlobalDistortion: (params: Partial<DistortionSettings>) => void,  // `amount` is Tone's `distortion` (direct write); `wet` is the stored Mix, tapered (squared, `colourWetGain`) and ramped over COLOUR_RAMP_SECONDS (50 ms) on the Distortion's branch of the Colour room
  setGlobalChebyshev: (params: Partial<ChebyshevSettings>) => void,  // `order` is rounded to a whole harmonic and clamped to 1..8; `wet` as for Distortion
  setGlobalBitCrusher: (params: Partial<BitCrusherSettings>) => void,  // `bits` (1..16) and the tapered `wet` both ramp over 50 ms
  setGlobalAutoWah: (params: Partial<AutoWahSettings>) => void,  // the envelope-follower wah; `Q`, `gain` and the tapered `wet` ramp over 50 ms, the rest are plain writes
  setGlobalPhaser: (params: Partial<Omit<PhaserSettings, 'sync'>>) => void,  // `rate` arrives in Hz (the store resolves a synced Rate first); `stages` is constructor-only in Tone, so a changed count rebuilds the node inside its bypass cell, behind a duck while the Phaser is heard
  setGlobalChorus: (params: Partial<Omit<ChorusSettings, 'sync'>>) => void,  // `rate` in Hz and `feedback` ramp; `delayTime` (ms) and `depth` ramp through the LFOs' range; `spread` is written behind a duck while heard; `wet` is the Double room's Return (`setRoomReturn`, linear)
  setGlobalTremolo: (params: Partial<Omit<TremoloSettings, 'sync'>>) => void,  // `rate` in Hz and `depth` ramp; `spread` behind a duck while heard; the tapered `wet` goes to the cell
  setGlobalVibrato: (params: Partial<Omit<VibratoSettings, 'sync'>>) => void,  // `rate` in Hz and `depth` ramp; the tapered `wet` goes to the cell
  setGlobalFrequencyShifter: (params: Partial<FrequencyShifterSettings>) => void,  // `shift` (signed Hz, clamped by sign) ramps; `wet` is the Shimmer room's Return (`setRoomReturn`, linear)
  setGlobalStereoWidener: (params: Partial<StereoWidenerSettings>) => void,  // `width` 0..1, never tapered, ramps; exactly 0.5 (unity) takes the widener out of the path
  setGlobalEQ: (params: Partial<EQ3Settings>) => void,
  setGlobalCompressor: (params: Partial<CompressorSettings>) => void,
  setGlobalLimiter: (params: Partial<LimiterSettings>) => void,
}
```

Note: there is no rig-wide bypass or per-effect enabled/bypass toggle. Both were removed — every effect's "off" state is fully expressible through its own params (a return level of 0 for reverb/delay, or a robot's own send at 0; a filter's own passthrough frequency, etc.), so a separate on/off flag was redundant. `GlobalAudioSettings` and its per-effect settings types carry no `enabled`/`globalBypass` fields. The Dark-Effect Bypass (roadmap 50.6, below under Signal Graph) is not a toggle either: an effect leaves the signal path by itself when its own Mix reaches 0 (Width: exactly 0.5), and nothing is stored for it.

Note: `note` is resolved to a validated pitch string (`/^[A-Ga-g][b#]{0,2}\d+$/`) before triggering — an invalid note is warned-and-skipped, not thrown.

### Key Guarantees

- **Singleton**: The exported `AudioEngine` object is the shared entry point for audio work in the app.
- **Polyphony Control**: The engine caps active voices at `MAX_POLYPHONY = 16` and skips additional notes when the cap is reached.
- **Lookahead**: Scheduling uses the shared `MIN_LEAD` constant (default `0.1s`) so notes are prepared ahead of playback time.
- **Idempotence**: `AudioEngine.start()` exits early once initialization has completed, so repeated calls do not duplicate setup.
- **Cleanup**: `AudioEngine.stop()` stops the transport and clears the playback tick; `AudioEngine.killAll()` performs the full reset by cancelling transport events, releasing voices, and resetting beat-clock state.

### Musical Time Authority

`beatClock.ts` does not wrap or proxy Tone.Transport — it has no Tone import at all. It polls `transport.position` off whatever transport-like instance `AudioEngine.start()` hands it via `initBeatClock(transport)`, and there is no `BeatClock` object to import; every function below is a **named export** from `beatClock.ts`. It serves as the single source of truth for musical time:
- All timing expressed in beats/measures, not seconds
- 1 beat = quarter note at current BPM
- 1 measure = 4 beats (4/4 time signature)
- Measures count music and the fleet's lifecycle, never a day: the in-world day is wall-clock (`DAY_DURATION_MS`, 6 real minutes), see [BEAT_CLOCK.md](BEAT_CLOCK.md)

**Never use `setTimeout`, `setInterval`, `requestAnimationFrame`, or `queueMicrotask` for musical timing.**

**For complete BeatClock implementation details, see [BEAT_CLOCK.md](BEAT_CLOCK.md).**

## Harmony System

The Harmony System provides dynamic 8-note palettes that cycle sequentially through a fixed 12-entry set as the transport's measure count advances — each entry holds for `MEASURES_PER_PALETTE_ENTRY` (2) measures before advancing to the next, wrapping back to the first once it reaches the end. This allows robot melodies to adapt without regenerating the melody events themselves.

**Key concepts:**
- Robots store note **indices (0-7)**, not pitch strings
- The active palette index is derived fresh from the transport's measure position every tick (never accumulated), so a missed tick self-corrects rather than drifting
- Melody events remain immutable; only the palette changes
- Updates are driven by BeatClock/Transport rather than timers, via `beatClock.ts`'s own `scheduleRepeat`/`cancelSchedule` — no locally-owned transport handle

**For complete Harmony System implementation details, see [HARMONY_SYSTEM.md](HARMONY_SYSTEM.md).**

## Melody Generation

Melody generation creates unique, procedurally-generated patterns for each robot at spawn time using index-based notation (0-7) that automatically adapts to harmony changes.

**Key concepts:**
- 16-step grid (1-measure loop, 16th-note quantized)
- Weighted index distribution (lower indices more common)
- Syncopation control (on-beat vs. off-beat preference)
- Step registry for O(1) playback lookup
- Melodies generated once at spawn, immutable after

**For complete Melody Generation implementation details, see [MELODY_SYSTEM.md](MELODY_SYSTEM.md).**

## Polyphony Management

Polyphony management controls the maximum number of simultaneous audio voices to prevent audio distortion, CPU overload, and maintain musical clarity.

**Key principles:**
- Global polyphony ceiling — `MAX_POLYPHONY = 16` at Full; the Robot Load slider can lower the *live* ceiling (`setPolyphonyCap`, see [Audio Load Budget](#audio-load-budget))
- Per-robot isolated composite voice (each robot owns its own sub-bus)
- Fail-fast skipping when limit exceeded
- Transport-based voice release scheduling
- Centralized enforcement in AudioEngine

**Why it matters:**
- Prevents audio distortion and CPU spikes
- Maintains musical clarity
- Ensures stable performance across devices

**For complete implementation details, see [POLYPHONY_GUIDE.md](POLYPHONY_GUIDE.md).**

**Skipped Notes debug counter — removed.** A bottom-left, dev-only overlay (`SkippedNotesCounter.tsx`) once showed how many note triggers were rejected per measure, backed by a `useDebugStore` rolling history. Originally added to diagnose the voice-release stall bug (see [BPM_CONTROL.md](tasks/BPM_CONTROL.md)'s "Post-launch addition: Skipped Notes debug counter"), then removed entirely (2026-09-16, Crawford's own request) along with `debugStore.ts` — `triggerWithCap`, `startMelodyPlayback`, and `playRegisteredEvents` no longer count skip reasons at all.

## Audio Load Budget

**Update 2026-09-22:** shipped as **two independent sliders**, Robot Load (`audioStore.robotLoad`) and Effects Load (`audioStore.effectsLoad`), each 0–1 with the same Light 0.2 / Standard 0.6 / Full 1 anchors. Robot Load drives `maxAudibleRobots`, `maxPolyphony`, and the boot-time latency hint; Effects Load drives drift and filter LFOs (the robot-LFO cap this line once also named is gone — `docs/tasks/LFO_BANK.md` Task 2). The three preset buttons still set both sliders together to one value, reproducing the original single-dial behavior exactly; dragging either slider alone moves only its own axis. Everything below that still describes one axis's mechanics is unchanged in substance — it now runs twice, once per axis. Built for the phone-only clicking and dropouts in [todo/scratchy-audio-phones.md](todo/scratchy-audio-phones.md). Full (both sliders) is exactly today's original behavior; everything is opt-down. Spec: [specs/AUDIO_LOAD_BUDGET.md](specs/AUDIO_LOAD_BUDGET.md); plan and deviations: [tasks/AUDIO_LOAD_BUDGET.md](tasks/AUDIO_LOAD_BUDGET.md); measurements: [PERFORMANCE.md](PERFORMANCE.md).

**The pure core** — `src/utils/audioBudget.ts` (constants only: no Tone, no stores, so `audioContextSetup` can use it before any Tone node exists). `robotLoadToLimits(robotLoad)` maps the Robot Load slider to `RobotLoadLimits`: `maxAudibleRobots` (2..12) and `maxPolyphony` (6..16) interpolate linearly; `latencyHint` is `playback` below `LOAD_PLAYBACK_BELOW` (0.4). `effectsLoadToLimits(effectsLoad)` maps the Effects Load slider to `EffectsLoadLimits`, exactly three fields: `driftEnabled` (`LOAD_DRIFT_MIN`, 0.8), `filterLfosEnabled` (`LOAD_FILTER_LFOS_MIN`, 0.4) and `busFilterLfosEnabled` (`LOAD_BUS_FILTER_LFOS_MIN`, 0.8; effective, so also false whenever `filterLfosEnabled` is — Robot Articulation T14b) — there is no `maxRobotLfos`/robot-LFO cap at all (`docs/tasks/LFO_BANK.md` Task 2 removed it; a robot link's cost no longer scales with count, so nothing left to cap). The two merge into the combined `LoadLimits` shape `describeLimits` and the diagnostics HUD read, each slider contributing its own independent value. `reconcileSounding` decides which robots sound (below); the LFO Bank's own `lfoEngine.setFilterLinksEnabled`/`setBusFilterLinksEnabled`/`setDriftEnabled` (next section) read `filterLfosEnabled`/`busFilterLfosEnabled`/`driftEnabled` directly rather than through an `audioBudget.ts` classifier — `lfoAllowed` left this file with the cap it existed to serve. `parseLoadParam` / `loadToSearchParam` / `withParam` (sets or clears one query key, `load` or `fxLoad`) / `resolveInitialAudioLoad` / `resolveInitialEffectsLoad` / `detectCoarsePointer` handle `?load=` / `?fxLoad=` and phone detection (a coarse primary pointer defaults both to Light).

**Which robots sound — first come, first served, solo excepted.** `audioBudgetSystem` (`src/systems/audioBudgetSystem.ts`, `startAudioBudget()` from `main.tsx`, before first power-on; not torn down by a power cycle) watches an `id:audioMode:docking` *signature* of the active locale's robots (not the robots — `updateRobot` rewrites the locale on every battery tick and swell write) plus `robotLoad` and the active-locale id (`effectsLoad` changes don't affect admission). It keeps eligible robots (`isRobotAudible`) in **arrival order** (`orderByArrival`), runs `reconcileSounding`, and pushes only real changes to `AudioEngine.setSoundingRobots()` and `audioStore.soundingRobotIds`. Incumbents keep their slot; a freed slot goes to the earliest waiter; a lowered cap evicts newest first; a soloed robot is admitted at once by evicting the newest non-solo robot; an explicit unmute of a docked robot does not jump the queue. Over-budget robots **stand by** — silent, but they keep swimming, draining and recharging (`isRobotAudible` is unchanged; the cards read the third state through `getAudibilityState` / `isRobotSounding`).

**Why gating is at the note trigger only.** `triggerWithCap` returns `false` for a robot outside a non-null sounding set, after the mute/solo check and before the polyphony test, so a standing-by robot never consumes a slot. No voice is built, released or rebuilt, so there is no build spike and no click when a robot changes state (releasing voice chains for standing-by robots is a deferred "Phase B" — measured a weak lever on its own). The cap applies to *new triggers only*: lowering `setPolyphonyCap` below the notes already sounding never forcibly releases them, which could strand the voice counter. `setSoundingRobots(null)` and the `MAX_POLYPHONY` default mean the engine behaves exactly as before until something pushes; `killAll()` leaves both alone.

**LFO tiers — three dial-driven flags, no per-robot cap.** There is no robot-LFO cap and no per-LFO suspend/connect policy — every seeded or user-made robot link primes unconditionally (`docs/tasks/LFO_BANK.md` Task 2 removed `ROBOT_LFO_CAP_*`/`maxRobotLfos` outright once the LFO Bank made a robot link's own cost a fixed, lane-amortized one rather than one-oscillator-per-target). What the dial still gates are the bank's own three flags: `lfoEngine.setFilterLinksEnabled(enabled)` suspends (disconnects, keeping the link record) every `lpf.*`/`hpf.*` link's Gain below `LOAD_FILTER_LFOS_MIN` (0.4) — EQ-gain links are never affected — and `lfoEngine.setDriftEnabled(enabled)` detaches every lane's rate-/depth-drift Gains below `LOAD_DRIFT_MIN` (0.8); and `lfoEngine.setBusFilterLinksEnabled(enabled)` suspends every robot's own `bus.frequency` link below `LOAD_BUS_FILTER_LFOS_MIN` (0.8), on top of the filter tier — a bus link is held off when either switch is off and comes back only when both are on, so Standard runs the global filter links but not the robots' own (Robot Articulation T14b; 0.8 is a placeholder until the phone A/B settles it). None of the three reacts to Robot Load. All are idempotent and reversible: suspending never touches a link's stored lane/depth or a lane's drift amount, only whether its Gain is currently wired into the graph, so restoring is immediate and exact. `audioStore.filterLinksHeldOff` (the Audio Rig's LPF/HPF links), `audioStore.busFilterLinksHeldOff` (the robot Filter subsection's Cutoff link) and `audioStore.driftHeldOff` (the four lanes' drift rows) are the three booleans the UI greys controls against — set by `audioBudgetSystem.applyLfoTiers` alongside the engine calls, not derived from engine state, so a panel can grey out before or after the audio actually changes without an extra subscription.

**Latency is a load-time decision.** A context's `latencyHint` is fixed at creation, so `audioContextSetup.ts` resolves it at page load: an explicit `?latency=` wins, otherwise the boot-time Robot Load preset (`?load=`, or detection) — Light installs `playback`, Standard and Full leave Tone's default. Changing either slider live never touches the context. Both sliders are mirrored into the address bar independently (`history.replaceState`, other params kept) — `?load=` for Robot Load, `?fxLoad=` for Effects Load, each omitted while at its own default — so a reload keeps them.

**UI.** The Audio Load panel (`AudioLoadPanel.tsx`, Fleet Params → Transport & Composition, next to Tempo) is one preset radio plus two 0–100 % sliders (Robot Load, Effects Load) over the two stored numbers, plus a `describeLimits` readout of their merged limits. The Audio Rig's LPF/HPF `LfoLink` pickers grey out (controls disabled, stored lane/depth kept) with a "Held off by Audio Load" label (`HeldOffNote`) while `filterLinksHeldOff` is true — EQ's own links and every robot layer link are never held off, since there's no cap left to enforce on them (the one robot link that is held off is the Filter subsection's Cutoff link, greyed against `busFilterLinksHeldOff` instead); Fleet Params → LFO Bank's four Rate Drift / Depth Drift rows grey out the same way while `driftHeldOff` is true (Shape/Rate never grey). Cards show "Standing by" for the robot-admission budget above, unrelated to any LFO state. The `?debug` overlay shows `audible n/12` and `load 20%·fx 100% · sounding 4/4 · standing by 2 · poly 3/8 · fx in 2/10` (the last token is the bypass cells' count, Signal Graph below), plus a `bank n/4   links n/n` line for the LFO Bank (see LFO Modulation below) and an `lfo drift on · filter on · bus off` line showing which of the three LFO tiers the Effects dial is holding off. `links` counts 7 slots per robot (`ROBOT_LFO_TARGET_IDS`, the six layer targets plus `bus.frequency`) on top of the 7 global ones, so twelve robots read `n/91`.

## Layered / Composite Voices and Visual Mapping

Trace Atlas uses serializable audio descriptors at spawn time so visuals and audio can share the same data without constructing Tone objects during render. The canonical descriptor is the robot's `audioAttributes.layers` array; visual shape/color/lamp props are computed live from `layers`/`adsr`/`waveform` at render time (`robotVisualHelpers.ts`, `RobotBody.tsx` — see docs/ROBOT_DESIGN.md), not stored on the robot. Roadmap Phase 36 removed an earlier spawn-time snapshot of these same values, which went stale the moment a Robot Options edit changed the ADSR it was computed from.

Key points:
- Each layer is an `OscillatorLayer` with `type` (a `WaveformType` — `'noise'` was removed in Roadmap Phase 9), `gain`, `detune`, `phase`, and optional `pulseWidth`. There is no separate `active` flag — `gain: 0` is how Coaxial/Harmonic are muted (Baseline always seeds a real, nonzero gain); see `filterAudibleLayers` below. There is no per-layer `adsr` field either — every layer shares the one envelope on `audioAttributes.adsr` (Roadmap Phase 9 collapsed Signature Array editing down to a single shared envelope per robot).
- Spawn-time logic in `src/systems/spawnSystem.ts` always generates exactly 3 layers (Baseline/Coaxial/Harmonic); robot visuals derive their body shape and lamp directly from the live `layers`/`adsr` at render time (`bodyShapeFromAdsr`, `calculateLampIntensity` — `robotVisualHelpers.ts`), not from anything computed at spawn.
- `AudioEngine.reserveVoice()` consumes those layers to create a runtime composite voice and route it through a per-robot sub-bus (panner → gain → filter → global chain entry, EQ3, plus five send gains tapped off the filter into the shared Reverb, Delay, Colour, Shimmer and Double rooms — see Signal Graph below). Its own `filterAudibleLayers` excludes any layer with `gain === 0` from the composite voice it actually builds (no synth node created for it) — muting a layer doesn't discard its configuration, which stays in `Robot` state untouched. Note the exclusion only applies the next time the voice is actually rebuilt (a Type change, or `reReserveVoice` for any other reason) — dragging Gain itself to exactly 0 goes through the continuous, no-rebuild path (`applyLayersContinuous`/`updateVoiceLayerParams`), so it silences immediately via a live gain write on the still-built node, and only gets excluded from the graph on the next real rebuild. The bus's own gain node is seeded from the optional `masterVolume` parameter (default `1`) and stays live afterward via `AudioEngine.updateRobotMasterVolume(robotId, masterVolume)` — a continuously-updatable AudioParam, not a value baked into any note's own trigger, so a live Volume edit (Robot Options) affects an already-sounding note's tail too, not just the next one. `masterVolume` (0–1, UI displays it as 0–100%) is never applied to the bus gain directly — it's passed through `robotBusGain()` (`src/engine/audioEngine/headroom.ts`) first: `volumePositionToGain()` (`src/engine/audioEngine/volumeTaper.ts`), a perceptual/logarithmic taper (position mapped to a dB offset, then to linear gain over a 40dB range) rather than a linear pass-through, then the fixed headroom trim, `HEADROOM_TRIM_GAIN` (−12 dB; see **Headroom** under Signal Graph). A robot at 100 % therefore sits 12 dB under unity. A linear mapping felt almost flat across most of the fader's travel, since human loudness perception is roughly logarithmic — real, shipped feedback caught post-launch.
- Composite voices expose `triggerAttackRelease`, `set`, and `dispose` semantics so scheduling code can use a single high-level API. The shared ADSR is applied at construction (`createCompositeVoice(descriptor, adsr, portamento)`, identically to every included layer) and can be updated live afterward via `AudioEngine.updateVoiceEnvelope(robotId, adsr)`, which reuses the same continuous-update `set({ layers })` path `updateVoiceLayerParams` uses for gain/detune/phase/pulseWidth edits — no audio gap. The envelope also carries the optional `attackCurve` / `releaseCurve` (an `EnvelopeCurveName`: linear, exponential, sine, cosine, bounce, ripple or step; absent = linear, today's sound). `toToneEnvelope` is the one place absence is handled: it hands Tone a curve only when one is present, so `set` never receives an `undefined` key (which would reset Tone's envelope). `audioAttributes.portamento` (seconds each layer glides into the next note; absent or 0 = none) is set on every layer synth at construction and live through `AudioEngine.updateVoicePortamento(robotId, seconds)`, again via `set({ layers })`. No Tone node is added by any of it: the phase builds one `Filter`, one `Panner`, one `Synth` per audible layer and the same `Gain`s as before (pinned in `AudioEngine.test.ts`).
- Because the mapping is stored on the robot as serializable data, visuals can be rendered in non-audio contexts without requiring Tone.js objects.

Recommended usage:
- At spawn: persist the generated `audioAttributes.layers` on the robot.
- At audio init: call `AudioEngine.reserveVoice(robotId, layers, adsr, phase, detune, pulseWidth, masterVolume)` to allocate an isolated composite voice. Reservation returns `false` only if voice creation fails; polyphony enforcement happens later when notes are triggered via `AudioEngine.scheduleNote()`.
- For a live Volume edit after reservation: call `AudioEngine.updateRobotMasterVolume(robotId, masterVolume)` rather than re-reserving — instant, affects anything currently sounding.
- For a live send edit after reservation (Reverb, Delay, Grit, Shimmer, Double): call `AudioEngine.updateRobotSends(robotId, { reverb?, delay?, grit?, shimmer?, double? })` — a ramp, not a re-reserve. A send is never "default", so every reservation path primes it from the robot with `robotSendLevels(robot)` (`src/data/robotSends.ts`: all five, in table order, straight off the robot; `reserveVoice`'s signature is not widened): the post-load pass in `loadInstruments`, `reReserveVoice` (inside it) and the two spawn reservations in `spawnSystem.ts`. `sessionDiff.ts`'s restore primes only the sends its diff carried, each through `engineKeyOf`.
- For envelope edits after reservation: call `AudioEngine.updateVoiceEnvelope(robotId, adsr)` rather than re-reserving — instant, no audio gap.
- For a glide or bus-filter edit after reservation: call `AudioEngine.updateVoicePortamento(robotId, seconds)` or `AudioEngine.updateRobotBusFilter(robotId, { frequency, Q, type })` — instant, no audio gap, no rebuild.
- In components: compute visual properties live from `audioAttributes` via `robotVisualHelpers.ts` (see docs/ROBOT_DESIGN.md); do not instantiate synths in components.

### Global volume vs. robot volume — two unrelated fields, one shared taper

`audioStore.volume` ([docs/specs/GLOBAL_VOLUME_CONTROL.md](specs/GLOBAL_VOLUME_CONTROL.md)) is **not** the same field as robot-level `masterVolume` above, despite both being called "volume" and both being passed through the same `volumePositionToGain()` taper. The robot side goes through `robotBusGain`, which applies the headroom trim after the taper; the master side takes the taper alone, so the master slider keeps unity at 100 % (roadmap 54, **Headroom** below). `audioStore.volume` (`[0, 1]`, default `1`, never persisted across sessions) is the master-output slider position shown next to the mute button in `TransportBar.tsx`, driving `AudioEngine.setMasterVolume()` — the final gain stage after the global FX chain, affecting every robot at once. Robot `masterVolume` is a per-robot bus gain, set independently per robot via Robot Options and `AudioEngine.updateRobotMasterVolume()`. The two are unrelated: changing one never affects the other, and there is no field that combines them — a robot's audible loudness is its own `masterVolume` attenuated a second time by the master `audioStore.volume` gain stage downstream.

`audioStore.setVolume(volume)` writes `volume` and calls `AudioEngine.setMasterVolume(volumePositionToGain(volume))`, always also clearing `isMuted` (dragging the slider while muted un-mutes as a side effect, jumping straight to the dragged-to level). `audioStore.setMuted(muted)` calls `AudioEngine.setMasterVolume(muted ? 0 : volumePositionToGain(volume))` without touching `volume` itself — mute and volume are fully independent controls; the mute icon reflects only `isMuted`, never slider position. `AudioEngine.setMasterVolume`/`getMasterVolume` themselves are unchanged by this feature — still a plain clamped-gain passthrough with no taper of their own; the taper is applied once, at the `audioStore` call site.

## Signal Graph

Two graphs compose: a **per-robot bus** (built per `reserveVoice` call) feeding a **global FX chain** (built once in `loadInstruments`, called from `start()`). The chain entry point is the **entry cut**, a zero-delay `Tone.Delay` that feeds EQ3, first in both topologies below (EQ3 itself when no `Delay` constructor exists, as in headless tests) — every robot bus connects into whichever node `src/engine/audioEngine/globalFx.ts`'s `getGlobalChainEntry()` returns (`AudioEngine.reserveVoice()`'s only caller), not a hardcoded compressor reference. The cuts are explained under **Global Pedals** below.

Five effects are **rooms**, not stages in the chain: the Reverb and the Delay (`Tone.Reverb`, `Tone.FeedbackDelay`, both permanently `wet: 1`; Robot Sends, roadmap 50.2, [docs/specs/ROBOT_SENDS.md](specs/ROBOT_SENDS.md)), and since Robot Effect Sends (roadmap 50.7, [docs/specs/ROBOT_EFFECT_SENDS.md](specs/ROBOT_EFFECT_SENDS.md)) the **Colour room** (the Distortion, Chebyshev and BitCrusher), the **Shimmer room** (the FrequencyShifter) and the **Double room** (the Chorus). They sit beside the chain: each robot taps its post-Volume, post-bus-filter signal into a room through its own **send** gain, and the room's output returns to the chain through a **return** gain. A robot at send 0 never reaches that room.

```
Per robot:  composite.output → panner → busGain → busFilter ─┬─ dry ──────────────────► entry cut (chain entry)
                                                             ├─ reverbSend  ─► Reverb room  ─► reverb return  ─┐
                                                             ├─ delaySend   ─► Delay room   ─► delay return   ─┤
                                                             ├─ gritSend    ─► Colour room  ─► grit return    ─┤
                                                             ├─ shimmerSend ─► Shimmer room ─► shimmer return ─┤
                                                             └─ doubleSend  ─► Double room  ─► double return  ─┤
Global dry chain (no room in it; [Name] = that effect in its bypass cell):                                     │
  entry cut → EQ3 → LPF → HPF → filter cut → [AutoWah] → [Phaser] → [Tremolo] → [Vibrato] →                    │
      Compressor → [StereoWidener] → Limiter → ceiling → masterGain → Destination                              │
  Natural Decay (default):  every return rejoins at the Compressor's input  ◄──────────────────────────────────┤
  Controlled Decay:         every return rejoins at the Width cell's input, skipping the Compressor ◄──────────┘

One cell:  in ─┬─► dry ──────────────────────────┬─► cut ─► (next stage)
               └─► effect (pinned wet) ─► wet ───┘     the effect's two edges exist only while it is lit

One room:  in ─┬─► effect (pinned wet) ─► wet ───┬─► cut ─► return ─► (join)
               └─► effect (pinned wet) ─► wet ───┘     no dry path; a branch's two effect edges exist only while it
                                                       is lit (the Colour room has three branches, the other two one)

busGain = robotBusGain(Volume): the Volume taper × the headroom trim.   ceiling = the output WaveShaper.   (Headroom, below)
```

Two fixed topologies, not a general reorder mechanism — selected by one boolean, `audioStore`'s `globalAudio.compressorBeforeDelay` (default `false` = Natural Decay, not seeded, only a direct user action changes it — a two-option radio button rendered inside `AudioRigDrawer`'s Compressor accordion, under its other params, not a toggle in the master row). The dry chain is identical in both; the toggle changes only **where the rooms' returns rejoin it**. `globalFx.ts`'s `wireGlobalFxChain(controlledDecay: boolean)` disconnects every node and reconnects the full sequence for whichever topology — called once at build time and again whenever `audioStore`'s `setCompressorBeforeDelay(value)` action flips it (a brief audio glitch on switch is expected and acceptable, since the user is intentionally changing routing). `disconnect()` on a room drops only its *outputs*, so the robots' send gains stay connected to the rooms' inputs across every flip; for the three effect rooms the flip drops and re-makes every edge from the room's `in` onward, while the edges into `in` are the send gains' own outputs and stay. A flip re-makes each bypass cell's and room branch's own edges as they were (`wireCells`): an effect that was lit is reconnected, a dark one is not.

**The in-app Decay Mode copy matches this wiring.** Natural Decay's echoes pass *through* the Compressor (they rejoin at its input) and Controlled Decay's bypass it (they rejoin at the Width cell's input, past the Compressor; the Limiter's input before Global Pedals, and still the fallback when no Width cell exists). The Output intro's Decay Mode item says so: under Controlled Decay the echoes have "only Width and the Limiter above them". The copy used to say the opposite, from before Robot Sends; it was corrected to the wiring (the Decay Mode list item and the radio's help in `fleet.ts`), not the other way round, so the sound did not change. Robot Sends kept the wiring-level behaviour of both modes exactly as it was (the old serial order had the same property: Natural put the Compressor *after* Delay and Reverb, Controlled before them). The rooms being off-chain also means the old "Controlled Decay moves Compressor before both Delay and Reverb" description no longer exists as a serial order.

**Sends and returns.** A robot has five sends (0–1, `Robot` fields; the Reverb, Delay, Grit, Shimmer and Double sliders after Pan in the Levels block, 0–100 %): `reverbSend`, `delaySend`, `gritSend`, `shimmerSend` and `doubleSend`. They are one table, `ROBOT_SENDS` (`src/data/robotSends.ts`, roadmap 55): each row names the `Robot` field, the key `updateRobotSends` takes (a `SendEngineKey`: `reverb`, `delay`, then the three rooms' `grit`, `shimmer`, `double`), the share-link code and the slider's content key, and every consumer iterates it in that one order: the reservation prime, the voice's send gains, the screen rows, the session diff, the share codec, the store clamp and the swell pool's tail. `ROBOT_SEND_FIELDS` is its field list, and `engineKeyOf` is the one translation from the robot's keys to the engine's (nothing maps back). They are the only way a robot reaches a room, so a robot at 0 is truly dry for that room: no echo, no reverb, no colour, no room processing of its signal at all. `SEND_MIN`/`SEND_MAX` bound them; `updateRobotSends` ramps them over `SEND_RAMP_SECONDS` (0.05 s). Each room's return gain is what its Fleet Params level sets: the Reverb and Delay *Amount* sliders (`globalAudio.reverb.wet` / `delay.wet`) and the Chorus and Shifter *Return* sliders (`chorus.wet` / `frequencyShifter.wet`), all default `1` and unseeded: how loud the whole room is, as heard from every probe. The Colour room's return stays at the `1` it is built with; each colour Mix is its branch's level instead (below). The per-robot depth is seeded at spawn from one table, `ROBOT_SEND_LOADING_RANGES` (`src/data/robotSendLoadingRanges.ts`), by `generateRobotSends` (`spawnSystem.ts`): Reverb in 0.1–0.6 on every robot (widened from 0.1–0.4 by the Classic Band Retune, 2026-10-21), Delay in 0–0.3 with a roll under 1 − its `lit` share (0.25) putting exactly 0 on a share of the fleet — about 17–18 % in practice, because the one noise sample behind the roll is bell-curved (left alone: the Reverb and Delay draws are byte for byte those of roadmap 50.2). Grit, Shimmer and Double are below. The whole addition is 60 send gains in a 12-robot fleet and five return gains; no per-robot effects.

**The three effect rooms (Robot Effect Sends, roadmap 50.7; [docs/specs/ROBOT_EFFECT_SENDS.md](specs/ROBOT_EFFECT_SENDS.md)).** Grit feeds the **Colour room** (the Distortion, Chebyshev and BitCrusher), Shimmer the **Shimmer room** (the FrequencyShifter) and Double the **Double room** (the Chorus). There are no new effect nodes: the five effects moved off the chain, and the additions are three send gains per robot plus an `in`, a zero-delay `cut` and a `return` per room. The Vibrato stays an insert.

- **A room is the bypass cell without its dry path** (`src/engine/audioEngine/bypassCell.ts`). `ROOM_KEYS` is `grit`, `shimmer`, `double`, and `ROOM_BRANCHES` says which of the ten `BYPASS_KEYS` are each room's branches (the other five are chain cells). `buildRoom` makes a room's `in`, `cut` and `return`; `buildBranch` makes each branch a `Cell` with no `dry` gain that shares the room's `in` and `cut`: `in` → the effect (pinned fully wet) → `wet` → `cut` → `return` → the join, where the Reverb and Delay returns rejoin. A branch's law is wet-only (`branchGains`). A colour branch's wet gain is its tapered Mix (`colourWetGain`), so each colour Mix is that effect's level as heard from every probe, like a Return. The Shimmer and Double branches are written `1` once at build, and their room's Return carries the level.
- **A branch is in the signal path only while its room is live and its own level is above 0.** A room is live while it is fed and its Return is above 0. Fed means some reserved robot sends into it above 0: `AudioEngine` keeps one feeder set per room (`roomFeeders`, module state, never in a store) and calls `setRoomFed` only when a set goes empty or non-empty, so a second feeder or a level change inside the room costs no crossing. `setRoomReturn` ramps a room's `return` over `COLOUR_RAMP_SECONDS`; `setGlobalChorus` and `setGlobalFrequencyShifter` write the Double and Shimmer Returns, and nothing writes the Colour room's. Whenever a room's liveness flips, every branch is re-written at its recorded level through the same `writeCellMix` crossing as a cell: connected while its wet gain is 0, disconnected after the ramp from the audio-clock timer. So a dark room costs what a dark effect costs. A Grit send is heard only in a world whose Colour character lit an effect (about three in four); otherwise every colour Mix is 0 and the three colour effects stay out of the path, Grit robots or not.
- **Wiring.** `reserveVoice` taps three more send gains off the robot's bus filter beside Reverb and Delay (all five are one record on the voice, `VoiceEntry`'s `sends`, keyed by `SendEngineKey` since roadmap 55) and connects each room send to its room's `in` (`getGlobalRoomInput`); a room that does not exist gets no edge. `releaseVoice`, and a voice replaced by a re-reservation, take the robot out of every feeder set. `loadInstruments` tells each room where its feeder set stands once the room is built, because robots reserved and primed at spawn joined the sets before any room existed (the Checkpoint C fix, `bd8c2ae6`: a share link's sends were inaudible). Every reservation site primes all five sends with `robotSendLevels(robot)`: the post-load pass, `reReserveVoice` and the two spawn sites; the session restore primes the sends its diff carried. `wireGlobalFxChain` connects each room's `return` to the join beside the Reverb and Delay returns; `disconnectAllFxNodes` lists each room's `roomNodes`, downstream first; each room's `cut` bounds a send's connect to that room (`chainCycleSearch.test.ts`).
- **Seeding.** A fresh robot rolls Grit, Shimmer and Double in that order (`EXCLUSIVE_SEND_FIELDS`), each a uniform draw under its `lit` share, and carries at most one: Grit 0.4–0.8 at 0.21, Shimmer 0.2–0.5 at 0.16, Double 0.3–0.6 at 0.19; everyone else sits at exactly 0. Every key is read on every robot, so the draw set never depends on the outcome. Measured on the 150 test worlds: 2.50 Grit, 1.62 Shimmer and 1.55 Double robots per fleet of twelve, and no Grit robot in 7.3 % of fleets. Crawford's listen (2026-10-22) kept the bands as built. On the global side the Chorus and the shifter lost their lit rolls (`PEDAL_LIT_EDGE`), their Returns come from the defaults, and the Chorus rolls its Sync in every world.
- **Controls.** Three more `0–100 %` rows after Delay in the Levels block on the robot and company screens (their schemas are rows of `ROBOT_SEND_SCHEMAS`; a slider writes through `applySend` and a swell through `applySendValue`, the one pair all five sends share since roadmap 55), broadcast-not-link on a company like every field. The Chorus and Shifter Mix rows read *Return*; the colour Mix rows keep their name and say they are each effect's level. The Colour drawer has no Return of its own (Crawford, 2026-10-21).
- **Persistence and swells.** The three sends save, share (`gr` / `sm` / `db`) and restore as the Reverb and Delay sends do (see [SESSION_STORAGE.md](SESSION_STORAGE.md)), and join the robot swell pool. Nothing on the robot body reads them.
- **Measured.** Desktop (T19, [todo/scratchy-audio-phones.md](todo/scratchy-audio-phones.md)): every room crossing ×0.84–×1.29 with no gap; an all-dark world reads `npm run perf:audio` 0.466 mean / 0.547 peak window against the base's 0.467 / 0.561; power-on, a Decay flip and a send crossing are no slower. About one connect in six, of any effect into the live graph (50.6's cells included), loses one render quantum in headless Chrome (backlog 29); Crawford heard no tick on real speakers. Pixel 8 (T21): at 3:00 the branch read 76, 62 and 59 underruns against the base's 48, 68 and 95. One branch run collapsed after 3:30 and its repeat did not; that is backlog 27's late collapse, which `main` shares.

**Colour (Global Colour, roadmap 50.3; [docs/specs/GLOBAL_COLOUR.md](specs/GLOBAL_COLOUR.md)).** Three single-instance saturators: `Tone.Distortion`, `Tone.Chebyshev`, `Tone.BitCrusher`. From roadmap 50.3 to 50.6 they sat on the **dry** chain between the High-Pass Filter and the Compressor; since Robot Effect Sends (roadmap 50.7) they are the three branches of the **Colour room**, heard only from the robots that send into it with Grit (above). The rooms are parallel, so the Reverb and Delay tails are never coloured. None of the three is an LFO or swell target: `lfo.ts`, `audioSwell.ts` and `audioSwellRanges.ts` name none of them, and nothing on the robot body reads them.

- **Fields.** `distortion.amount` (0–1, Tone's `distortion`) and `distortion.wet`; `chebyshev.order` (an integer, 1–8) and `chebyshev.wet`; `bitCrusher.bits` (an integer, 1–16) and `bitCrusher.wet`. `oversample` is `'none'` on both shapers, explicitly and always, with no control for it. Every setter clamps a value into the field's full range and ignores a non-finite one (a share link is untrusted input, and an `order` of 1e9 would stall the shaper-map build), rounds `order` to a whole harmonic, is null-guarded and try/caught, and is a no-op when its node was not built.
- **The Mix is tapered.** The stored `wet` is the slider position (0–1) and the effect receives it **squared** (`colourWetGain`, `bypassCell.ts`; the squared value sets the effect's branch gain in the Colour room since roadmap 50.7, and set its bypass cell in 50.6, never the node's own `wet`): 0 silences the effect, 1 is the whole effect, and half the slider is a quarter of it. On the Pixel the three were far too strong across a linear slider (Crawford, 2026-10-15). Only the Mix is tapered: `amount`, `order` and `bits` are not. The stored value, the seed bands and the share codes all keep meaning "slider position". `wet` and `bits` ramp over 50 ms (`COLOUR_RAMP_SECONDS`) against clicks; `amount` and `order` are direct writes.
- **The worklet.** `Tone.BitCrusher` is the app's first `AudioWorklet`. It is constructed behind `getToneCtor`, inside a `try`: if a browser refuses it the slot is skipped, a `devWarn` is logged, and the chain wires without it. Its processor registers asynchronously, so for a fraction of a second at boot its wet path is empty; at `wet` 0 nothing changes.
- **A fresh world is seeded by one character.** `COLOUR_CHARACTERS` is `clean`, `drive`, `fold`, `crush`, picked from one draw (`globalAudio.colour.character`) through `COLOUR_CHARACTER_BANDS` (0.3065 / 0.5 / 0.6935 / 1, about 25 % each). **At most one effect is on in any world** (Crawford, 2026-10-15; the spec first drew three pair characters too, about 15 % of worlds, and they were dropped). The lit effect's Mix seeds in its loading band, one shared band for all three, 0.1–0.2 (a wet layer of −36 to −24 dB; pulled back from the Classic Band Retune's first 0.2–0.35 after Crawford's listen, "much more subtle"), and **no seeded Mix is above 0.25** (`COLOUR_LOAD_MIX_MAX`; this governs a fresh world only, a saved session or share link restores what was hand-set). Every other effect seeds Mix 0 but still draws its shape value (`amount` 0.1–0.35, `order` 2–5, `bits` 6–10), so a hand nudge of Mix hears something at once. The edges are set by measurement, not by fraction: the character draw is bell-curved and discrete (about 190 distinct values), so nominal edges gave 10 / 34 / 18 / 30 / 4 / 4 / 0 % over 20 000 styles; `COLOUR_CHARACTER_BANDS`' own comment records the fit and how to redo it. `DEFAULT_GLOBAL_AUDIO_SETTINGS` and the three transmission presets are dry (every Mix 0, `amount` 0.3, `order` 2, `bits` 8).
- **Persistence.** The three blocks are part of `globalAudio`, which travels whole. A payload saved before they existed loads them dry (`withGlobalAudioDefaults`; see [SESSION_STORAGE.md](SESSION_STORAGE.md)).
- **Phone.** One Pixel 8 run at Full, 3:00, with no clipping and no underruns reported. It was verbal: the world, the HUD numbers, a Standard run, the re-baseline on current `main` and the desktop `npm run perf` comparison were not recorded (see `docs/todo/scratchy-audio-phones.md`). No `LOAD_COLOUR_MIN` threshold was built, because nothing reported a rise.

**Modulation (Global Modulation, roadmap 50.4; [docs/specs/GLOBAL_MODULATION_COLOUR.md](specs/GLOBAL_MODULATION_COLOUR.md)).** Two single-instance pedals sit on the **dry** chain, after the filter cut and before the Tremolo (between BitCrusher and the Compressor until roadmap 50.7), wah first: `Tone.AutoWah` (`autoWah`), an envelope follower sweeping a bandpass to the fleet's own dynamics, then `Tone.Phaser` (`phaser`), a stack of allpass notches swept by its own LFO. They are in the chain in both Decay Modes (`wireGlobalFxChain`'s `chainNodes` and `disconnectAllFxNodes`' list), before the points where the rooms' returns rejoin, so the rooms' tails are never swept. Nothing is per robot, and neither pedal is an LFO or swell target: `lfo.ts`, `audioSwell.ts` and `audioSwellRanges.ts` name neither, and nothing in the gem folder or `RobotBody` reads either.

- **Fields.** `autoWah.baseFrequency`, `autoWah.octaves`, `autoWah.sensitivity`, `autoWah.Q`, `autoWah.gain`, `autoWah.follower`, `autoWah.wet`; `phaser.rate`, `phaser.octaves`, `phaser.baseFrequency`, `phaser.stages`, `phaser.Q`, `phaser.wet`. Every Tone parameter is a slider (Fleet Params gains a Modulation tab between Colour and Output, on the existing `spectral` trait; there is no new trait). The setters (`setGlobalAutoWah`, `setGlobalPhaser`) clamp into the field's full range, ignore a non-finite value, and are null-guarded and try/caught like Colour's.
- **The Mix is tapered the same way.** `wet` is the slider position and the pedal's bypass cell receives `colourWetGain(wet)` (squared). The seed bands are the pedals' own: they no longer share Colour's `COLOUR_LOAD_MIX_MAX` (Crawford, T16, 2026-10-15), so a fresh world may seed a pedal Mix of 0.35–0.5 (AutoWah) or 0.3–0.4 (Phaser); the floors rose at the Classic Band Retune (2026-10-21) because the bottom third of a squared slider is near silence.
- **The Phaser rebuilds on a Stages change.** `stages` is constructor-only in Tone, so `setGlobalPhaser` builds a new node first with the last-written value of every other field, swaps it inside the Phaser's bypass cell (`rebuildPhaser`; the rest of the chain, the returns and the join are not touched), and only then disposes the old node; a failed rebuild keeps the old node. While the Phaser is heard the swap waits at the bottom of a duck (`writePhaserStages`, see **The bypass cells**), so a lit Phaser goes dry for about 0.15 s per change and through a drag; a dark one is rebuilt at once. If the new node cannot be connected, its cell drops to fully dry and Mix 0, and the next Mix write lights it like any dark cell. Boot builds the Phaser twice (the default 10 stages, then the seeded count through `applyGlobalAudioToEngine`).
- **The Phaser's Rate is the third Free | Sync field.** `PhaserSettings.sync?` is a note value (absent = Free). The engine hears Hz only: `resolveSyncedRateHz(phaser, bpm, PEDAL_RATE_RANGE_HZ)` in `src/utils/tempoSync.ts` gives the Hz, the store's `setPedalSyncMode('phaser', …)`, `syncedRateToSync` and `syncedRateToFree` convert, and a tempo change re-pushes a synced Rate. Its LFO is wall-clock (the LFO Bank's accepted class), not on the transport. See [specs/FREE_SYNC_TOGGLE.md](specs/FREE_SYNC_TOGGLE.md).
- **A fresh world lights each pedal about a third of the time, independently.** `PEDAL_LIT_EDGE` (one edge per pedal, nominal 1/3, measured 33.07 % and 33.30 % over 20 000 styles) on two uniform draws, independent of each other and of Colour's character. A dark pedal seeds Mix 0 but still draws every other field from its band. About half of lit Phasers seed Sync (`PEDAL_SYNC_ODDS.phaser`, measured 50.2 %); a dark Phaser is always Free. All the pedals' draws are uniform (`getUniformSeededVal`), because the plain draw is coarse and correlated across keys.
- **Persistence.** Both blocks are part of `globalAudio`, which travels whole. A payload saved before they existed loads them dry (`withGlobalAudioDefaults`), and an invalid `phaser.sync` is dropped on restore (see [SESSION_STORAGE.md](SESSION_STORAGE.md)).
- **Phone.** One Pixel 8 run at Full, 3:00, both pedals at full Mix and 12 stages: some underruns (count not recorded) and no distortion, by Crawford's word. The world, the HUD numbers, a Standard run, runs (a) and (b), the T0 re-baseline and the desktop `npm run perf` comparison were not recorded (see `docs/todo/scratchy-audio-phones.md`). Crawford closed the gate on that evidence, so the gate's "zero underruns at Full" was not met as worded and no baseline shows whether the pedals raised the count. No `LOAD_PEDAL_MIN` threshold was built.

**Global Pedals (roadmap 50.6; [docs/specs/GLOBAL_PEDALS.md](specs/GLOBAL_PEDALS.md)).** Five more single-instance effects. Four motion pedals: `Tone.Chorus` (`chorus`, two LFO-swept delay lines, a flanger once it has feedback), `Tone.Tremolo` (`tremolo`, LFO-swept loudness, the two channels apart by the Spread), `Tone.Vibrato` (`vibrato`, an LFO-swept short delay, a pitch wobble) and `Tone.FrequencyShifter` (`frequencyShifter`, single-sideband ring modulation, every partial moved by the same number of Hz). Roadmap 50.6 put all four on the **dry** chain after the Phaser; since Robot Effect Sends (roadmap 50.7) the Chorus is the **Double room** and the shifter the **Shimmer room** (above), and only the Tremolo and the Vibrato stay on the chain, after the Phaser and before the Compressor. The returns rejoin after them in both Decay Modes, so the rooms' tails are never swept. The fifth, `Tone.StereoWidener` (`stereoWidener`, Width), is a mid/side stage between the Compressor and the Limiter. Under Controlled Decay the returns now join at its cell's input rather than the Limiter's, so Width hears the rooms in both modes, and Width 0 folds everything to mono for a phone speaker. None is an LFO or swell target, and nothing in the gem folder or `RobotBody` reads any of the five. Each is a sub-tab: Modulation has six, in chain order (AutoWah, Phaser, Chorus, Tremolo, Vibrato, Shifter), and Output has three (Compressor, Width, Limiter).

- **Fields and setters.** `chorus.rate`, `chorus.delayTime` (ms), `chorus.depth`, `chorus.spread` (degrees), `chorus.feedback`, `chorus.wet` go to `setGlobalChorus`; `tremolo.rate`, `tremolo.depth`, `tremolo.spread`, `tremolo.wet` to `setGlobalTremolo`; `vibrato.rate`, `vibrato.depth`, `vibrato.wet` to `setGlobalVibrato`; `frequencyShifter.shift` (signed Hz, −1000 to 1000) and `frequencyShifter.wet` to `setGlobalFrequencyShifter`; `stereoWidener.width` (0–1, 0.5 is unity) to `setGlobalStereoWidener`. `rate` is Tone's `frequency`, named so that every Free | Sync pair is `rate` + `sync`. Every setter clamps into the field's full range, ignores a non-finite value (the shift is clamped by its sign), and is null-guarded and try/caught. The Tremolo and Vibrato `wet`s are tapered (`colourWetGain`); the Chorus and shifter `wet`s are their rooms' Returns since roadmap 50.7, linear like the Reverb's; Width is never tapered, so 0.5 stays unity. The Shift row is a centred-zero slider on a signed-log track (`logKnee: 1`, [COMPONENT_LIBRARY.md](COMPONENT_LIBRARY.md)), which gives the seeded ±2–20 Hz band 28 % of each half.
- **Ramps, not steps.** Every rate, the Tremolo and Vibrato Depth, the Chorus Feedback, the Shift and the Width ramp over `COLOUR_RAMP_SECONDS`. Tone's own Chorus `delayTime` and `depth` setters step each LFO's range, which jumps the delay's read position (×217 and ×13 the steady waveform's peak second difference, offline), so `rampChorusSweep` ramps the same range on the two LFOs' internal Scale Signals instead (×1), and falls back to Tone's setters if those internals are not there. The Spread of a lit Chorus or Tremolo swaps both LFOs' waveform at once and cannot be ramped, so it is written at the bottom of a duck (see **The bypass cells**).
- **The LFOs run always.** The Chorus and Tremolo are `start()`ed once when built (Tone does not start them), and the Vibrato starts its own. A dark pedal is Mix 0, never a stopped LFO, and no pedal LFO is `sync()`ed to the transport: Sync is a resolved Hz. Their phase is wall-clock, the LFO Bank's accepted class. Out of the signal path a dark pedal's LFOs still run; that is most of the 38 ‰ that all ten dark effects still cost (below).
- **Stereo.** The Chorus, Tremolo and Vibrato keep left and right apart. The shifter is half mono: Tone negates its sine branch into an AudioParam (`Add.addend`), which the browser downmixes, while its cosine branch stays stereo. A centred voice shifts cleanly; a hard-panned one leaks the other sideband at a third of the wanted one and puts both, at a quarter level, in the far channel (measured, spec §8). Crawford's listen kept it as it is (spec §7 Q1).
- **Three more Free | Sync rates.** `ChorusSettings`, `TremoloSettings` and `VibratoSettings` carry an optional `sync` note value like the Phaser's. `SYNCED_RATE_KEYS` (`phaser`, `chorus`, `tremolo`, `vibrato`, in `src/types/globalAudio.ts`) is the one list the store, the drawer, the seeder and the session sanitiser loop over. The store resolves a synced rate with `resolveSyncedRateHz(block, bpm, PEDAL_RATE_RANGE_HZ)` before the setter hears it, `setPedalSyncMode(key, synced)` switches a pedal between Free and Sync, and a tempo change re-pushes each synced rate. All four share one range, `PEDAL_RATE_RANGE_HZ` (0.05–10 Hz, step `PEDAL_RATE_STEP_HZ`, 0.05). See [specs/FREE_SYNC_TOGGLE.md](specs/FREE_SYNC_TOGGLE.md).
- **A fresh world lights at most two Modulation pedals.** After the AutoWah and Phaser rolls, which are unchanged, the Tremolo and then the Vibrato roll their own uniform draw under `PEDAL_LIT_EDGE` (0.25 each) and are forced dark once two of the four are lit (`MAX_LIT_PEDALS`). Every roll is read on every style, so the draw set never depends on the outcome. Measured over 20 000 styles: Tremolo 22.04 %, Vibrato 19.55 %, two lit in 33.20 % of worlds and never three. (Until roadmap 50.7 the cap counted six, with the Chorus at 0.25 and the shifter at 0.15.) About three quarters of lit Tremolos seed Sync, whose Free rate would beat against the 16th grid, and about half of lit Vibratos (`PEDAL_SYNC_ODDS`, one entry per pedal; measured 75.14 / 49.73 %); the Chorus rolls its Sync in every world (49.51 %), since any robot may light its room. The shifter's sign is a draw of its own. A dark pedal seeds Mix 0 and still draws its other fields, so a hand nudge of Mix hears a seeded sound; the Chorus and the shifter draw every field but their Return in every world. Width has no roll: a fresh world seeds 0.4–0.65, and in about 4 % of worlds that lands on exactly 0.5, which is unity and so dark. By hand any number of pedals can be lit.
- **Persistence.** The five blocks are part of `globalAudio`, which travels whole. A payload saved before they existed loads them at the defaults (Tremolo and Vibrato Mix 0, the Chorus and shifter Returns 1, Width 0.5), and an invalid `sync` is dropped on each of the four synced blocks (see [SESSION_STORAGE.md](SESSION_STORAGE.md)). An older payload's Chorus or shifter Mix loads as the Return it now is. The defaults and the three transmission presets are clean: Tremolo and Vibrato Mix 0, the Chorus and shifter Returns at 1 (heard only through a robot's send), Width 0.5.

**The bypass cells (the Dark-Effect Bypass, part of roadmap 50.6; [docs/specs/DARK_EFFECT_BYPASS.md](specs/DARK_EFFECT_BYPASS.md)).** A Tone `Effect` processes its wet path at any `wet`, Mix 0 included, so before 50.6 every effect on the chain cost its full price in every world. On the Pixel, the branch with every new pedal dark but still inline read 380 underruns at 3:00 and then collapsed, where `main` read 94 ([todo/scratchy-audio-phones.md](todo/scratchy-audio-phones.md), Global Pedals round 2). Now each of the ten effects (`BYPASS_KEYS` in `src/engine/audioEngine/bypassCell.ts`: the three Colour effects, the AutoWah, the Phaser and the five pedals) sits in a four-node cell: `in` → `dry` → `cut`, and `in` → the effect → `wet` → `cut`. The effect is built pinned fully wet (the widener at unity), so the cell's two gains carry the Mix. Since roadmap 50.7, five of the ten (`ROOM_BRANCHES`) are room branches instead, cells with no `dry` path (see **The three effect rooms** above); the other five are the chain cells described here.

- **Dark means out of the signal path.** A Mix of exactly 0 is dark, and so is a Width of exactly 0.5. A dark effect's two edges do not exist, so the audio thread never reaches it. EQ3, the LPF and the HPF stay in at neutral (backlog 28).
- **The law.** A Mix effect's cell follows Tone's own `CrossFade`, equal power: `dry = cos(w·π/2)`, `wet = sin(w·π/2)` for the tapered `w = colourWetGain(mix)` (`cellGains`). A lit effect sounds as it did before the cells (offline render, every difference ≤ 1.8e-7). Below a Mix of about 0.04 Tone's own law kept a −56 dB wet floor that the cell does not, so a dark effect is now fully dry. Width's cell fades linearly (`widthCellGains`), since both of its paths carry the same signal at unity. A Mix ramp longer than a quarter of the law (π/8) is split into chords so that the level dips at most 0.17 dB on the way.
- **The crossing.** `writeCellMix` is the one place a Mix reaches a cell. Lighting connects the effect while the wet gain is at 0, so the new path is silent, then ramps to the law. Darkening ramps to dry, then disconnects from Tone's audio-clock timer (`Tone.getContext().setTimeout`, as `scheduleVoiceRelease` uses it) once lookAhead, the ramp and `BYPASS_DISCONNECT_MARGIN_SECONDS` have passed, so the wet gain has reached 0 on the audio thread first. A parameter de-click, not musical timing. A re-sent value with nothing to do writes nothing, so `applyGlobalAudioToEngine`'s whole-block re-sends neither ramp nor re-arm. Measured in a real-time context, every crossing of all ten effects is inaudible (worst ×1.19 against a bar of ×1.6).
- **The duck.** Some changes an effect cannot make smoothly while it is heard: the Chorus and Tremolo Spread (a waveform swap) and a Phaser Stages change (a node swap). `duckCell` ramps a heard cell to dry, applies the change from the same audio-clock timer once the ramp has run, and ramps back to the latest Mix. Each step of a drag re-arms the one timer, so only the last value lands and the pedal is dry for about 0.15 s at a 0.1 s lookAhead, longer through a drag. A cell out of the signal path takes the change at once.
- **Every cell ends in its own zero-delay cut.** Tone's `standardized-audio-context` searches every path downstream of a node on each `connect` and `disconnect` and stops only at a node with a `delayTime`, so the path count multiplied stage by stage: with the five pedals inline, power-on was estimated at about 14 minutes of main thread. Two chain cuts (`CHAIN_CUT_OPTIONS`: the entry cut and the one after the HPF, where the global LFO targets end) and a cut per cell bound every search to one stage. A delay of 0 outside any cycle passes the sound unchanged. `src/engine/audioEngine/chainCycleSearch.test.ts` is a tripwire on the library's behaviour, so an upgrade that changes it fails the suite instead of hanging power-on.
- **Measured.** All ten dark cost 38.3 ‰ of a desktop core in their cells, against 150.6 inline in the same sitting; `npm run perf:audio` reads below `main`; power-on and a Decay flip are no slower. On the Pixel, a world with everything dark reads at or below `main`. A run late in a sitting collapses on both builds, `main` included, which is backlog 27.
- **The HUD.** The `?debug` overlay's budget line ends ` · fx in n/10`: how many of the ten effects are in the signal path, chain cells and room branches alike (`getConnectedEffectCount`, a darkening effect counts until its disconnect fires; the denominator is `BYPASS_KEYS.length`).

**Headroom (roadmap 54; [OUTPUT_HEADROOM.md](specs/OUTPUT_HEADROOM.md)).** Before it, on the loudest measured world the fleet's summed dry signal peaked at +12.8 to +14.5 dBFS after the chain's EQ (`pre`, which that world's EQ boosts by +3.5 to +4 dB), and the master sat at or over full scale in 22–25 % of readings, which the browser hard-clips (the crunch). Two fixed pieces keep the output under full scale, edited worlds included:

- **The trim.** Every robot's bus gain is `robotBusGain(masterVolume)`: the Volume taper times `HEADROOM_TRIM_GAIN`, `HEADROOM_TRIM_DB` = −12 dB (`src/engine/audioEngine/headroom.ts`). It is computed at all three places a bus gain is set: `reserveVoice`'s bus (the real `Gain`, or the stub made without a `Gain` constructor), its composite-failure fallback, and `updateRobotMasterVolume`'s ramp. It lives on the bus rather than at the chain entry because the five room sends tap off the bus: the trim scales each robot's dry and wet alike, so every send balance stays put and only the level moves (a trim at the entry would make every room 12 dB wetter). The master slider keeps the bare taper and unity at 100 %.
- **The ceiling.** A `Tone.WaveShaper` after the Limiter and before `masterGain`, in both Decay Modes (`buildGlobalFxChain`, the `_ceiling` slot; `wireGlobalFxChain`'s `chainNodes`; `disconnectAllFxNodes`' list). Its curve, `softCeilingCurve()` (4097 entries), is the identity up to `CEILING_KNEE`, 0.7 (−3.1 dBFS), so ordinary signal passes bit-exact, and above it a tanh that approaches full scale and never reaches it: an input at or past full scale leaves at 0.928 (−0.65 dBFS). Tone takes the curve as `mapping`; a `curve` option is ignored and leaves the node empty, which is why T5.1 exists. Oversample is the node's default, `'none'`. A missing constructor (headless) skips the ceiling and a throwing one skips it with one `devWarn`, as for any node. The `?debug` overlay's `out` tap hangs off `masterGain`, so it reads after the ceiling; `pre` is unchanged.
- **Why the Compressor and Limiter could not do it.** Web Audio's compressor, which both `Tone.Compressor` and `Tone.Limiter` wrap, applies automatic makeup gain from its own curve, so a deeper setting can raise the level; and Tone's Limiter (20:1, 3 ms attack, 10 ms release, knee 30) is a soft compressor, not a ceiling. Both stay the user's, musical, and seeded as before, except that Checkpoint A raised the seeded Compressor release to 0.25–0.3 s: a 70 ms release under 13–17 dB of gain reduction, with every robot Volume at 100 %, bent the waveform ([reference/GLOBAL_CHAIN_GRID.md](reference/GLOBAL_CHAIN_GRID.md)).
- **Not a setting.** Neither piece is seeded, stored, saved, shared or shown. The cost is level: the master's RMS is 6.6–7.0 dB lower on the loudest measured world and 0.2–0.7 dB lower on `bravo`, made up on the device.
- **Measured** ([PERFORMANCE.md](PERFORMANCE.md), "Output level series"): on five seeded session-link worlds and two pushed by hand (EQ +12 dB, Limiter at 0, every robot at 100 %), the master never reached full scale: −0.6 dB at most, on a hand push. `main` reached +4.6 dB on an untouched world and +7.3 dB on the hand push. The ceiling's audio-thread cost is below what `npm run perf:audio` resolves; on the Pixel, at the phone's own Light tier, the branch and `main` swapped order between two worlds, which is the run-to-run spread, not a cost ([todo/scratchy-audio-phones.md](todo/scratchy-audio-phones.md)).

Control the global chain via `AudioEngine.setGlobal*` (see API above) for individual effect parameters — there is no separate bypass surface (the cells above follow each effect's own Mix); `audioStore.setCompressorBeforeDelay` (not part of the `AudioEngine` surface — it calls `globalFx.ts` directly) for the topology swap.

The per-robot `panner` is refreshed once per 16th-note tick from the robot's live GSAP x (`updateAllPanners`), but the pan is only *written* when it has changed by more than `PAN_WRITE_EPSILON` since the last write — Tone's `Param.value` setter is `cancelScheduledValues` + `setValueAtTime`, and robots are stationary most of the time. `busFilter` is a per-robot `Tone.Filter` with the robot's own cutoff, resonance and type. Cutoff is `audioAttributes.filterFreq` (2000–8000 Hz for most robots, 400–2500 Hz for the roughly one in five accent robots: `spawnSystem`'s `OPEN_FILTER_FREQ_RANGE` and `ACCENT_FILTER_FREQ_RANGE`); resonance is `filterQ` (absent = `ROBOT_BUS_FILTER_Q`, 1; accent robots seed 3–8); type is `filterType` (absent = lowpass; an accent robot is a bandpass 40 % of the time, never highpass, though a user may pick it). `resolveBusFilterCutoff`, `resolveBusFilterQ` and `resolveBusFilterType` (`audioEngine/busFilter.ts`) are the only places absence becomes a value. All three reach `reserveVoice` from every reservation path (spawn, `reRegisterAllRobotsAudio`, `reReserveVoice`, the post-load pass) — the cutoff positionally, Q and type in the trailing `articulation` object beside `portamento`. Nothing on the gem reads any of it (see ROBOT_DESIGN.md). From the composite-voice rewrite until 2026-09-30 the cutoff was hardcoded to 1,200 Hz and `filterFreq` had no audible effect at all; a caller that omits it still gets that legacy value. `0` means "no filter" (opened to 20 kHz). It is live: `AudioEngine.updateRobotBusFilter(robotId, { frequency?, Q?, type? })` ramps cutoff and Q over `FILTER_RAMP_SECONDS` (0.05 s) and assigns the type outright (a type switch on a sounding voice may click; accepted), and is a safe no-op with a devWarn when the robot is not reserved — the store holds the truth and every reservation path re-reads it. The Source → Filter subsection (`BusFilterDrawer`) exposes Cutoff, Resonance and Type, plus an LFO link for the Cutoff (`bus.frequency`, see LFO Modulation).

## LFO Modulation — the LFO Bank

**Four shared, world-level, app-lifetime LFOs ("lanes") replace one private `Tone.LFO` per modulation target** (`docs/specs/LFO_BANK.md`, `docs/tasks/LFO_BANK.md`; shipped 2026-10-01, superseding everything the prior per-target design — including the old 2-group Drift pools — documented in this section). A target no longer owns an oscillator; it *links* to a lane and stores a depth. Built across two files: `src/engine/lfoEngine.ts` (the bank engine — lanes, links, and the Audio Load Budget's two LFO flags; renamed from `lfoBank.ts` once the old per-target `lfoEngine.ts`/`lfoDrift.ts`/`src/systems/robotLfoPriming.ts` were deleted outright) and `src/engine/lfoShared.ts` (unchanged connection-safety helpers — `centeredSwingFromRange`, `connectAdditively`, `isAudioContextRunning`, `clamp`).

### Target ids

14 targets total, defined in `src/types/lfo.ts`, each traced to a reference grid:

- **`RobotLfoTargetId`** (7, from [ROBOT_DATA_GRID.md](reference/ROBOT_DATA_GRID.md)'s `Has LFO` column): `'layer{0,1,2}.{gain,detune}'` plus `'bus.frequency'` (the robot's bus filter cutoff, Robot Articulation 50.1; the one robot target outside the layers, it rides the Audio Load Budget's filter and bus tiers and is not a swell attribute). Was 13 at launch, then 9 (`docs/specs/LFO_LOAD_FIX.md` cut `volume` and every `layerN.pulseWidth`), then 6 (`docs/tasks/LFO_BANK.md` Task 1 cut every `layerN.phase` — Phase never had a live Signal to modulate; see below), then 7 when `'bus.frequency'` arrived. Every removed id can still arrive from an old session/share link; the loaders drop it and the engine resolves it to nothing.
- **`GlobalLfoTargetId`** (7, from [GLOBAL_CHAIN_GRID.md](reference/GLOBAL_CHAIN_GRID.md)'s `LFO?` column, unchanged by the Bank): `'eq3.low'`, `'eq3.mid'`, `'eq3.high'`, `'lpf.frequency'`, `'lpf.Q'`, `'hpf.frequency'`, `'hpf.Q'`. Uses its own `'lpf'`/`'hpf'` short form, not `GlobalAudioSettings`' `filterLPF`/`filterHPF` field names. Neither Compressor, Reverb, Limiter, nor Delay's `delayTime` ever gets one.

`LfoLink` is `{ lane: LfoLaneId | null; depth: number }` — `lane: null` means not in the graph at all; `depth` is `0–100%` (`LFO_DEPTH_MIN/MAX`). This is what every target now stores, replacing the old per-target `LfoSettings` (`{ shape, rate, depth }`) entirely — shape and rate moved to the lane (below).

### The bank: 4 lanes, each an always-running LFO

`LfoLaneId` is `'a' | 'b' | 'c' | 'd'` (`LFO_LANE_IDS`) — order-carrying (the seed leans `a > b > c > d`, see Seeding); user-facing names (Core/Companion/Accent/Overtone LFO) live in `src/content/` (`ui.lfoLane`, `fleet.lfoBank.laneA`–`.laneD`), never in engine code. `BankLfoSettings` is `{ shape, rate, rateDrift, depthDrift, sync? }` — `rate` is `LFO_RATE_MIN..LFO_RATE_MAX` (`0–20` Hz; `0` is a legal user value, the lane just holds still — the seed never emits it), `rateDrift`/`depthDrift` are `-1..1`, and the optional `sync` is a tempo-synced note value (absent = Free; see "Free | Sync" below — the engine only ever sees the resolved Hz).

Built once per lane by `primeLfoBank(settings)`, called from `AudioEngine.start()` (below) — never rebuilt or disposed for the app's lifetime, and a no-op before the AudioContext is running or on any call after the first successful one. Per lane:

```
lane LFO (±1, amplitude pinned to 1) → trunk Gain (rests at 1) → one link Gain per linked target → connectAdditively(signal)
                                              ↑ depth-drift Gain
drift secondary LFO (0.03 Hz, fixed phase spread) → rate-drift Gain → lane LFO's own frequency
```

The lane oscillator's own amplitude never moves — depth lives entirely in each link's own Gain (`clamp(depth, 0, 100) / 100 × swing.max`, `swing` from `centeredSwingFromRange` against the target's current value, same formula and bug history as the old per-target design below). A lane's **drift** secondary (fixed `0.03`Hz, phase spread `360 / 4` degrees apart across the 4 lanes, never exposed in the UI — only the drift *amount* is) feeds two Gains: rate-drift back into the lane LFO's own `frequency` Signal, depth-drift into the **trunk's** gain (not the lane LFO's amplitude, which is pinned) — wobbling the lane's own shared amplitude wobbles every link hanging off it together, by design (`docs/specs/LFO_BANK.md` assumption 4). `refreshLaneDrift(lane)` recomputes both Gains' values from the lane's current rate/drift amounts after every `setBankRate`/`setBankRateDrift`/`setBankDepthDrift` call and after `primeLfoBank`.

### lfoEngine API

`lfoEngine`, exported from `src/engine/lfoEngine.ts`, is a plain object (no class, matching `AudioEngine`'s own shape):

```typescript
export const lfoEngine = {
  // Bank
  primeLfoBank: (settings: Record<LfoLaneId, BankLfoSettings>) => void,
  setBankShape: (lane: LfoLaneId, shape: LfoShape) => void,
  setBankRate: (lane: LfoLaneId, hz: number) => void,              // clamped to [0, 20]
  setBankRateDrift: (lane: LfoLaneId, value: number) => void,      // clamped to [-1, 1]
  setBankDepthDrift: (lane: LfoLaneId, value: number) => void,     // clamped to [-1, 1]
  getBankSettings: (lane: LfoLaneId) => BankLfoSettings,
  // Links
  linkTarget: (target: LfoTargetId, link: LfoLink, robotId?: string) => boolean,
  unlinkTarget: (target: LfoTargetId, robotId?: string) => void,
  disposeRobotLinks: (robotId: string) => void,
  // Audio Load Budget (see the section above) — suspend/restore, never edit stored state
  setDriftEnabled: (enabled: boolean) => void,
  setFilterLinksEnabled: (enabled: boolean) => void,
  setBusFilterLinksEnabled: (enabled: boolean) => void,
}
```

- **`getBankSettings`** never constructs a node — falls back to `DEFAULT_BANK_LFO` (`{ shape: 'sine', rate: 0, rateDrift: 0, depthDrift: 0 }`, `src/data/lfoConfig.ts`) until `primeLfoBank` has run.
- **`linkTarget` disables `Signal.override` before connecting — the actual root cause of the worst LFO bug found in this system, unchanged by the Bank rewrite.** Verified directly against Tone.js's own source (`signal/Signal.ts`'s `connectSignal()`): connecting *anything* to a `Tone.Signal` whose `override` flag is `true` — the class default, and every global-chain target (`Tone.Filter.frequency`/`Q`, `Tone.EQ3`'s bands) is a `Signal` — makes Tone immediately `cancelScheduledValues` + `setValueAtTime(0, 0)` on the destination and permanently mark it "overridden," **before the connected LFO has even started oscillating, and regardless of what `min`/`max` are set to.** For a filter's frequency Signal, that's a step change to an invalid `0` Hz cutoff the instant `.connect()` runs — every time, independent of any timing. `src/engine/lfoShared.ts`'s `connectAdditively(source, destination)` is the fix, shared by every connection this module makes (lane → trunk, drift → lane/trunk, trunk → link Gain, link Gain → target Signal/Param): it sets `override = false`, connects, then writes the destination's pre-connect value straight back — a harmless no-op for a `Signal` (never touched once `override` is disabled) and the actual fix for a `Tone.Param` (robot targets — `Tone.Gain.gain` — which has no `override` escape hatch and still resets unconditionally on connect, but is never permanently locked out the way an un-fixed `Signal` is).
- **`linkTarget`** resolves the live Signal via `AudioEngine.getRobotModulationTarget(robotId, target)` / `AudioEngine.getGlobalModulationTarget(target)` (returns `false`, never throws, if neither resolves — e.g. a robot-scoped target called with no `robotId`, or a lane that hasn't been primed yet), then sizes the link Gain's value from `centeredSwingFromRange()`: an **additive delta bounded by the target's CURRENT value and its distance to the nearer edge of its own range** (`min(currentValue - rangeMin, rangeMax - currentValue)`), never the field's raw absolute range — the same fix this app shipped three times historically for three different fields (LPF frequency's full `20–20000` span pushing the cutoff past Nyquist; a fixed symmetric swing still overshooting an off-center base value; `volume`'s now-removed target sitting exactly on its own range's edge, where the swing was unconditionally zero). Robot fields resolve from `ROBOT_LFO_FIELD_RANGE` (gain `0–2`, detune `±50` cents — the two surviving targets); global targets reuse `GLOBAL_AUDIO_SEED_RANGES`, translating `lpf.`/`hpf.` target ids to that table's `filterLPF.`/`filterHPF.` keys. A depth-only edit on an already-connected lane/signal pair updates the Gain's value in place — no reconnect, no click; a lane change or a rebuilt voice's new Signal tears down and reconnects.
- **`unlinkTarget`**/**`disposeRobotLinks`** reverse `linkTarget` — disconnect and dispose the link's Gain(s). Both are safe/no-ops on an unknown key; `disposeRobotLinks` is the "this robot is gone for good" call `localeStore.ts`'s remove/clear paths make.
- **`setDriftEnabled`/`setFilterLinksEnabled`/`setBusFilterLinksEnabled`** are the Audio Load Budget's three flags — see that section above for the thresholds and what greys in the UI. All only ever suspend/restore a Gain's connection; stored lane/link state is never touched. `isFilterTarget` (`/^(lpf|hpf|bus)\./`) names the links the filter tier can suspend; `isHeldOff` adds the bus switch for `bus.` links only, and `reconcileFilterLinks` re-suspends or restores after either switch moves, so a bus link is connected only when both switches are on.

Phase has no live Signal at all (`Tone.Oscillator.phase` is a plain get/set number, not a `Signal`/`Param`) — rather than the control-rate polling fallback the old per-target engine ran for it, Phase was cut from `RobotLfoTargetId` entirely (`docs/tasks/LFO_BANK.md` Task 1) and stays a plain, non-modulatable slider. `pulseWidth` was cut earlier, for cost (`docs/specs/LFO_LOAD_FIX.md`) — `Tone.PulseOscillator.width` is a real Signal, but only for `'pulse'`-type layers, and the per-pulseWidth-LFO cost (~7× any other robot LFO) made it the first target removed once priming made robot-LFO cost real.

### Free | Sync — anchoring a lane's rate (and Delay Time) to the tempo

Each lane's Rate and the global Delay's Time can run **Free** (a plain Hz / seconds value, as always) or **Synced** — shown to the user as **Anchored** — a note value of the tempo (a quarter, a dotted eighth, one bar) whose rate follows `audioStore.bpm`. Spec `docs/specs/FREE_SYNC_TOGGLE.md`, plan `docs/tasks/FREE_SYNC_TOGGLE.md`, Roadmap Phase 33. There are five toggles in the whole app — the four lanes and Delay Time — and no robot, company, link, or other effect has one.

- **Data.** `BankLfoSettings.sync?: NoteValue` (`src/types/lfo.ts`) and `DelaySettings.sync?: NoteValue` (`src/types/globalAudio.ts`). **Absent means Free**, and a Free result carries no `sync` key at all — never `sync: undefined` — so every pre-Sync session and share link loads Free with no migration. The Free value (`rate` / `delayTime`) is kept underneath a synced one, so flipping back never loses it. A `NoteValue` is `{ division, modifier }` (`src/data/noteValues.ts`); `NOTE_VALUES` is the fixed list of 20 (`1/32` … `1/2` and one bar, each straight / dotted / triplet, plus 2 and 4 bars straight-only), in 4/4 (`beatClock.ts`'s `BEATS_PER_MEASURE`, a bar is 4 beats), ordered by duration. `isNoteValue(x)` is the guard for anything untrusted.
- **The engine stays Hz-only.** `lfoEngine` and the Delay node never learn about sync. `src/utils/tempoSync.ts` holds the pure resolvers that turn a stored value plus the tempo into the plain float the engine receives, and they are the **only** sanctioned readers of a lane's `rate` or the Delay's `delayTime` for audio or on/off decisions: `resolveLaneRateHz` (a synced lane's note at the tempo, clamped into `0–20` Hz — a tempo past the cap clamps, it never stops the lane), `resolveLaneForEngine` / `resolveLfoBankForEngine` (the engine-facing copy: rate resolved, `sync` stripped), `resolveDelayTimeSeconds` (clamped into `DELAY_TIME_RANGE_SECONDS`, `0–10` s — the real cap, matching `globalFx.ts`'s `maxDelay: 10`), and `isLaneRunning` (a synced lane is always running whatever its stored rate; `audioDiagnostics.readBankRunning` counts with it). Every `sync` read goes through `isNoteValue`, so a corrupt value resolves Free rather than being trusted.
- **Where a value reaches the engine** (`audioStore.ts`). `setLfoBank` reads the *merged* lane back and resolves it, so a Free-rate edit on an already-synced lane re-sends the synced Hz; `replaceLfoBankLane(lane, settings)` is the whole-lane write plus a full push — the one path a Sync → Free change and a session restore use, because a `setLfoBank` merge cannot delete a key; `setLfoBankLaneSyncMode(lane, synced)` and `setDelaySyncMode(synced)` are the toggles, converting with `laneToSync` / `laneToFree` and `delayToSync` / `delayToFree` (Free → Sync snaps to the nearest allowed note; Sync → Free keeps what was heard, quantised to the slider step and, for a lane, floored at one step so a slow note can't round to a stopped lane); `setBPM` re-applies every synced value (`reapplyTempoSyncedValues`); and `applyGlobalAudioToEngine(globalAudio, bpm)` plus `lfoEngine.primeLfoBank(resolveLfoBankForEngine(lfoBank, bpm))` do it at power-on, after a seed, and on a session restore. Nothing is pushed on render, and every push is synchronous — no timers.
- **Allowed notes.** `allowedLaneNoteValues(bpm)` (slowest → fastest, within `0–20` Hz) and `allowedDelayNoteValues(bpm)` (shortest → longest, within `0–10` s) are the lists the Sync slider steps through. They depend on the tempo, so their callers memoize them on `bpm`. A stored note the current tempo has pushed out of its list is *displayed* at the nearest stop (the audio clamps independently); nothing is written back, so returning the tempo restores the stored note.
- **Drift.** `RATE_DRIFT_APPLIES_TO_SYNCED = true` (`tempoSync.ts`): a synced lane keeps its Rate Drift, which nudges it slightly off the grid. It is the single switch — set to `false`, `resolveLaneForEngine` hands the engine `rateDrift: 0` for a synced lane.
- **UI.** `TempoSyncSlider` (`src/components/ui/controls/TempoSyncSlider.tsx`) — the slider (Free: the caller's own schema; Sync: the allowed notes as its stops, the note's name as the readout) with `TempoSyncToggle` in a row of its own under it. Rendered for a lane's Rate in `LfoBankLanePanel.tsx` and for Delay Time in `AudioRigDrawer.tsx`'s Delay block. See [COMPONENT_LIBRARY.md](COMPONENT_LIBRARY.md).
- **Persistence.** `sync` rides in a saved session whole and in a share link as a compact code; a `sync` that isn't a real note is dropped at the restore boundary. See [SESSION_STORAGE.md](SESSION_STORAGE.md).

### Wiring — priming order matters

`AudioEngine.start()`, after `buildGlobalFxChain()` and its own re-apply of seeded effect *values* (`applyGlobalAudioToEngine(globalAudio, bpm)` — needed first, since `linkTarget`'s swing math reads each target's current value, and a synced Delay resolves against the tempo): `lfoEngine.primeLfoBank(resolveLfoBankForEngine(lfoBank, bpm))` (a synced lane is primed at its note's Hz at the current tempo, `sync` stripped), then one `linkTarget` call per `GLOBAL_LFO_TARGET_IDS` entry from `globalLfoLinks`, then (a second dynamic import, `primeRosterLinks(getActiveLocaleRobots())` from `src/systems/robotLfoLinks.ts`) every active robot's stored `lfoLinks`. Priming the bank before linking is load-bearing — `linkTarget` returns `false` for a lane that doesn't exist yet — and is covered by a call-order test, not just code review.

`src/systems/robotLfoLinks.ts` is the robot-side counterpart: `applyRobotLinkToEngine(robotId, target, link)` (the single call both a user edit — `robotOptionsActions.applyLayerLfoLink` — and priming route through), `primeRobotLinks(robot, targets?)` (re-applies one robot's stored `lfoLinks`, skipping any target the robot has no entry for rather than synthesizing a default), and `primeRosterLinks(robots)` (every robot once — no round-robin ordering needed, unlike the old priming, since there's no cap left to protect). Called at every point a robot's voice is (re)reserved — `spawnRobot`, `reRegisterAllRobotsAudio`, `AudioEngine.start()`'s roster pass, `applyLayersStructural` (a layer-type rebuild) — and by `applySessionPayload` (re-primes only the overridden targets). `localeStore`'s robot-remove/clear paths call `disposeRobotLinks` alongside the unrelated voice-teardown call.

### Seeding

- **Bank lane settings** (`src/utils/globalAudioSeed.ts`'s `generateLfoBankSettings(attenuationStyleId, attenuationStyleName)`) sample the Attenuation Style noise map, one call per lane, dataIds `lfoBank.<lane>.{rate,shape,rateDrift,depthDrift}`. Each lane's rate is drawn from its own fixed, adjacent, log-spaced band (`LFO_BANK_RATE_BANDS`: a `0.1–0.4`, b `0.4–1.5`, c `1.5–4`, d `4–8` Hz) — slow-to-fast by lane letter, quantized to `LFO_RATE_STEP` (0.05) — unaffected by shape. `rateDrift`/`depthDrift` sample `LFO_BANK_DRIFT_SEED_RANGE` (`±0.7`) quantized to a whole hundredth, also unaffected by shape. Re-seeds on Attenuation Style switch via the same `audioStore` subscription every other seeded field uses; `AudioEngine.start()` is what actually primes the engine from it (above) — AS-sync itself is data-only.
- **Sync rolls** (same two seeders — `generateLfoBankSettings` and `generateGlobalAudioSettings`): each lane and the Delay also rolls Free vs Sync from the Attenuation Style map, at dataIds `lfoBank.<lane>.syncMode` / `.syncNote` and `globalAudio.delay.syncMode` / `.syncNote`, against `LFO_BANK_SYNC_ODDS` (`globalAudioSeed.ts`; targets a/b/c/d = 75 / 66 / 33 / 25 %, so the slow lanes lean Anchored and the fast ones lean Float — the constants are calibrated per lane because a simplex draw isn't uniform, and the comment records every measured raw share) and `DELAY_SYNC_ODDS` (66 %). A synced lane's note is picked by `pickSeedNoteValue` (`tempoSync.ts`) from its own rate band at the style's seed tempo (`generateAttenuationStyleBpm`), falling back along `LFO_BANK_SYNC_BAND_ORDER` (own band, next faster, next slower, outward) should a band hold no note at that tempo; Delay's from its loading band (`0.05–0.5` s). The lane's Free `rate` is still sampled exactly as before, and every existing dataId and draw order is untouched, so a world that rolls Free is byte-identical to what it was before Sync existed (pinned by the oracle tests in `globalAudioSeed.test.ts`).
- **Shape is a weighted rotating-queue pick across one Attenuation Style's 4 lanes** (`src/utils/lfoShapeDraw.ts`'s `pickShape(t, queue)`, Crawford's melody-system-style "send the picked one to the back" scheme, 2026-10-02 — replaces the earlier `LFO_LOADING_SHAPES` two-shape restriction). All 4 `LfoShape` members are reachable from load now. Lane a draws first against the full queue `LFO_SHAPE_SEED_ORDER` (`[sine, triangle, sawtooth, square]`) weighted by `LFO_SHAPE_SEED_BIAS` (`[1, 0.5, 0.25, 0.125]` — each queue position half as likely as the one before it, so a fresh lane a is sine 53%/triangle 27%/sawtooth 13%/square 7% of the time); whichever shape gets picked is moved to the back of the queue before lane b draws, and so on through d — a shape can still repeat across lanes in the same world, just less likely each time it's reused, never forbidden. This is scoped to shape only: it has no bearing on rate, rateDrift, or depthDrift, which stay exactly as described above.
- **Global-chain links** (`generateGlobalLfoLinks`, same file) sample the Attenuation Style map per `GLOBAL_LFO_TARGET_IDS` entry: a quiet roll (`LFO_QUIET_THRESHOLD = 0.34`, i.e. **66% on-odds**) decides `{ lane: null, depth: 0 }` vs. a real lane pick. **A lit global target (the EQ, LPF and HPF fields) may only link the Core LFO (lane `a`) or, at most once per world, the Companion (lane `b`); it never links the Accent or Overtone lanes** (Crawford, 2026-10-21). Each lit target's lane draw is uniform and asks for the Companion when it falls under `GLOBAL_LFO_COMPANION_EDGE` (0.1) while no target has taken it yet, and the Core otherwise; measured over 20 000 styles, 5.06 targets are lit per world, 40.5 % of worlds carry one Companion link, 8.0 % of lit links are Companion and none are Accent or Overtone. A lit target then draws a depth in one of three per-group loading windows (below). This governs a fresh world only: a saved session or share link restores whatever lane was hand-set, and the robot-level links below keep the four-lane weighted `pickLane(t, counts)` draw (`src/utils/lfoLaneDraw.ts`: weight `LFO_LANE_SEED_BIAS[lane] / (1 + counts[lane])`, the `a > b > c > d` order bias `{ a: 1, b: 0.85, c: 0.7, d: 0.55 }` and a running `tallyLanes` tally).
- **Robot links** (`generateRobotLfoLinks(noiseMap, offset, priorLaneCounts)`, `spawnSystem.ts`) use the same `pickLane`/`tallyLanes` machinery at a different quiet threshold — `LFO_QUIET_THRESHOLD = 0.7`, i.e. **30% on-odds** for the six layer targets (`bus.frequency` has its own, rarer `LFO_BUS_QUIET_THRESHOLD = 0.8` via `robotLfoQuietThresholdForTarget`, about 1.6 robots in 12 lit) (correcting `docs/specs/LFO_LOAD_FIX.md`'s earlier, now-superseded "25%" figure for the same per-target coin flip) — and a `priorLaneCounts` argument that is **roster-aware, not reset per robot**: `spawnRobot` tallies every already-spawned robot's own `lfoLinks` in the active locale before generating a new one's, and each robot's own earlier targets update that same running tally as its own 7-target loop goes, so even one robot's own picks lean away from each other, not just away from the rest of the roster (one sentence on this also lives in [PROCEDURAL_GENERATION.md](PROCEDURAL_GENERATION.md)). A respawn-copy source's `lfoLinks` are kept wholesale, never regenerated, mirroring the rest of `AudioAttributes`'s copy behavior.
- **Depth seed ranges are per-group on both sides, not one flat window** (Crawford's own load-value tuning pass, 2026-10-02). Global links: `eq3.*` draws from `GLOBAL_LFO_EQ_DEPTH_SEED_RANGE` (`5–30%`), `lpf.frequency`/`hpf.frequency` from `GLOBAL_LFO_FILTER_FREQUENCY_DEPTH_SEED_RANGE` (`5–60%`), `lpf.Q`/`hpf.Q` from `GLOBAL_LFO_FILTER_Q_DEPTH_SEED_RANGE` (`5–40%`) — all three in `globalAudioSeed.ts`, sharing the `GLOBAL_LFO_DEPTH_SEED_MIN` floor of `5`. Robot links: Gain draws from `ROBOT_LFO_GAIN_DEPTH_SEED_RANGE` (`1–60%`), Detune from `ROBOT_LFO_DETUNE_DEPTH_SEED_RANGE` (`1–10%`), the bus cutoff from `ROBOT_LFO_BUS_DEPTH_SEED_RANGE` (`1–40%`, a filter moves the tone far more than a same-sized gain or detune nudge) — all in `spawnSystem.ts`, sharing the `ROBOT_LFO_DEPTH_SEED_MIN` floor of `1`. Every range's floor is deliberately nonzero: a lit target (one that didn't roll quiet) is never seeded silently inaudible, on either side — a user may still drag Depth to `0` by hand. All six ranges quantize to `LFO_DEPTH_STEP` (1, a whole percent); neither seeder ever reaches the engine by itself — see Wiring above for what actually primes it.

## Audio Swells

**Does this app have an LFO on a robot's Delay or Reverb?** No — but it has something else that moves them sometimes. Audio Swells is a wholly separate mechanism from LFO Modulation above: no `Tone.LFO`, no `Signal`/`Param` connection, no `Signal.override` concern at all. Neither a robot's `reverbSend`/`delaySend` nor the global `delay.wet`/`reverb.wet` ever gained a real `lfoEngine.ts` target — Audio Swells is the "something else," and it moves the two **robot sends** (since Robot Sends, roadmap 50.2). The global `wet` sliders used to be swell targets themselves; they are now fixed return levels and left the global pool. A "swell" is a rare, discrete, self-reversing event: one parameter ramps up from its current value, then ramps back down, landing **exactly** back where it started — never a net change, and never a continuous oscillation. Built entirely in `src/systems/audioSwells.ts` (types in `src/types/audioSwell.ts`, the robot-only range table in `src/data/audioSwellRanges.ts`), mirroring `robotSystems.ts`'s `startRobotLifecycle`/`stopRobotLifecycle`/tick lifecycle shape rather than anything in `lfoEngine.ts`. Every write goes through the exact call a human editing that control by hand would make (`audioStore`'s `setGlobalAudio` for global targets, `robotOptionsActions.ts`'s `applyVolume`/`applyLayersContinuous`/`applyAdsr` for robot targets) — so the relevant slider visibly crawls on its own while a swell is active on it, for free, with no dedicated UI.

### Two independent pools

- **Global pool** (`SWELL_GLOBAL_TARGET_IDS`, `types/audioSwell.ts`) — 7 targets, exactly the `GlobalLfoTargetId`s (`eq3.low`/`mid`/`high`, `lpf.frequency`/`Q`, `hpf.frequency`/`Q`; `SwellGlobalTargetId = GlobalLfoTargetId`). There used to be nine: `delay.wet` and `reverb.wet` were swell targets with an off-equivalent gate (`isGlobalTargetAtOffEquivalent`, so a `wet` at `0` was never picked and a mid-swell drop to `0` cancelled it). Both are gone: the global `wet` values are fixed return levels now (see Signal Graph), the depth of each robot's echo is its own send, and the swells moved there (Robot pool below). No remaining global target has an off-equivalent, so every one is always eligible — 0dB EQ and a wide-open filter passthrough frequency are common, legitimate resting positions, not "this effect is off" signals. A session saved mid-swell stores each global target's captured base rather than the interpolated value (`applyGlobalSwellBasesToAudio`, `sessionDiff.ts`); that helper lost its Delay and Reverb blocks with the targets.
- **Robot pool** (`SWELL_ROBOT_ATTRIBUTE_IDS`) — 22 attributes × the whole roster, never scoped to one robot: `volume`, each of the 3 layers' `gain`/`detune`/`phase`/`pulseWidth` (13 fields), 4 ADSR sub-fields (`adsr.attack`/`decay`/`sustain`/`release`), each independently eligible — never one atomic "envelope" move — and the five sends, `reverbSend` and `delaySend` (Robot Sends) then `gritSend`, `shimmerSend` and `doubleSend` (Robot Effect Sends), each group appended last so no earlier index moved (the tail is spread from `ROBOT_SEND_FIELDS` since roadmap 55). Spelled out as its own union since 2026-09-30 (`types/audioSwell.ts`'s own doc comment), **not** derived from `RobotLfoTargetId` — that union has since shrunk to 6 and then gained `'bus.frequency'` (`layer{0,1,2}.{gain,detune}` plus the bus cutoff, which is the one robot LFO target that is not a swell attribute; see LFO Modulation above), but Audio Swells is a separate system with no `.connect()`/Signal concept at all, so none of the LFO-cost reasoning that shrank `RobotLfoTargetId` applies here; `volume`, every `pulseWidth`, and every `phase` stay swell-eligible even though none of them can carry an LFO link any more. A swell just calls `applyLayersContinuous` with a new plain number on a `BeatClock` tick, the same as `SignatureArrayDrawer.tsx`'s own Phase slider. A robot attribute is only pickable if its own field, and anything it structurally depends on, is actually live — `layerN.*` requires that layer's own gain to be nonzero (`isRobotAttributeStructurallyLive`, replacing the removed `OscillatorLayer.active` flag — this makes `layerN.gain` itself self-referential: a muted layer's own gain can never be picked back up by a swell, matching the old flag's same "manual intervention only" behavior); `volume` and the 4 ADSR fields have no such parent and are always eligible; a send is live only while its stored value is above `0` (a robot seeded with no Delay never has one swell in, mirroring the layer-gain rule; checked at selection only, as for every robot attribute). A send swell lands exactly on its base like any other: the tick writes the stored 0–1 fraction through `applySendValue(robot, localeId, field, fraction)` (the percent action `applySend` delegates to it), because converting to a percent and back does not return the identical double for about 15 % of values. A hand edit of a send cancels that robot's swell on it first, in the caller (`RobotScreen`, `useCompanyOptions`), exactly as Volume does. Robot Ping Controls (`rhythmicDensity`, `rhythmicMotifLength`, `noteVariance`, `octaveRange`) are never in the 22-attribute pool to begin with — nothing excludes them at selection time because there's nothing to exclude.

Each pool has its own independent 5-concurrent-swell cap (`MAX_CONCURRENT_SWELLS_PER_POOL`) — a full global pool never blocks a robot swell from starting, and vice versa. Compressor and Limiter are never eligible in either pool, the same dynamics-processor exclusion `lfoEngine.ts` already applies; Delay's `delayTime` stays excluded too, and the Reverb and Delay rooms have no global swell target at all (their depth is each robot's send, in the robot pool).

### Direction, magnitude, and duration

Every swell-eligible attribute follows the same default rule, computed by `pickSwellPeakDelta` (used by the global pool and the robot pool's single-robot path) — a **new, from-scratch formula**, deliberately not `lfoShared.ts`'s `centeredSwingFromRange` (that one computes a *symmetric, bounded* swing with no directionality or minimum-swing guarantee, the wrong shape here):

- **Direction:** up if the current value is at or below the field's own midpoint, down if at or above it, a seeded coin-flip tie-break exactly at the midpoint.
- **Magnitude:** the peak is drawn somewhere between a 50%-of-range floor — relative to the *current value*, not the range's own midpoint (e.g. a field at 33% of its range swells up into `[83%, 100%]`) — and the true edge (min or max, matching direction).
- **Shape:** two phases only, rising then falling, computed in `advanceGlobalSwell`/`advanceRobotSwell` — no hold/plateau. Each tick's value is computed directly from `elapsed / totalPhaseMeasures` against the swell's own captured `baseValue`/`peakDelta`, never accumulated, and snapped to exactly `baseValue` once the swell's total duration elapses — the return-to-base is exact, not asymptotic.
- **Duration:** the Duration slider (`audioStore.swellDuration`, see below) sets the swell's **total** length in measures — rising + falling together — the same value for every attribute, the two sends included. `pickSwellSplit` (`audioSwells.ts`, docs/specs/AUTOMATION_FREQUENCY_DURATION_SPLIT.md §1.4) draws only the **split ratio** between the two phases, randomized per swell within `[0.2, 0.8]` (`SWELL_SPLIT_MIN_FRACTION`/`SWELL_SPLIT_MAX_FRACTION`) so the split still varies swell-to-swell even though the total no longer does. 1 measure is a hard floor on any phase, for any attribute, full stop (`pickSwellSplit`'s own `Math.max(1, ...)` on each side).

**Four attributes get their own exception**, each a pure clamp on the final peak or a swap of the magnitude formula — never a gate on direction-picking, so the up-vs-down choice itself is always the plain midpoint rule above:

| Attribute | Exception | Constant |
|---|---|---|
| Robot `volume` | A downward swell's peak is clamped so it never drops below 50% of Volume's own range | `VOLUME_SWELL_DOWNWARD_FLOOR` |
| Robot `layerN.detune` | The magnitude formula itself swaps out — capped to a **maximum** of 25% of detune's full range (±25 cents out of -50..50), the opposite shape from the default's "at least 50%" minimum | `DETUNE_SWELL_MAX_SWING_FRACTION` |
| `hpf.frequency` | An upward swell's peak is clamped so it never exceeds 4kHz | `HPF_SWELL_UPWARD_CEILING_HZ` |
| `lpf.frequency` | A downward swell's peak is clamped so it never drops below 100Hz | `LPF_SWELL_DOWNWARD_FLOOR_HZ` |

`clampVolumeDownward`/`clampGlobalPeak` apply the two clamp-shaped exceptions via two small shared helpers, `clampSwellFloor`/`clampSwellCeiling` — each guards against a currentValue that's already past the limit by collapsing to zero movement rather than flipping the swell's direction (e.g. an HPF already above 4kHz never gets pushed *down* by the ceiling clamp; it just doesn't move). Detune's exception is structurally different — not a clamp on `pickSwellPeakDelta`'s own output but an entirely separate magnitude function, `peakDeltaCappedByFraction`, selected by `robotPeakDeltaForDirection` (checked against every `layerN.detune` id via a shared pattern) instead of the default `peakDeltaForDirection` — direction still comes from the same `pickSwellDirection` helper both magnitude functions share.

`ROBOT_SWELL_FIELD_RANGE.volume` is `{0, 1}` (the store's real `masterVolume` fraction) — deliberately **not** the engine-internal LFO field range `volume` once had back when it was a real `RobotLfoTargetId` (`{0, 2}`, the fixed `Tone.Gain(1)` mix-stage node's own operating range; `lfoEngine.ts`'s own `ROBOT_LFO_FIELD_RANGE` has no `volume` key at all today, `volume` having been cut as an LFO target — see LFO Modulation above): reusing that old table would have silently bound a Volume swell against the wrong domain. `applyVolume`'s own parameter is the UI's 0-100 display percent, not this 0-1 fraction — `writeRobotValue` converts (`value * 100`) at the call site.

### Company-wide variant

A small chance turns a robot-pool pick into a **company-wide** swell instead of a single-robot one — the same attribute, moving in lock-step, across every eligible robot in one randomly-chosen `Company`. Not a separate pool, cadence, or cap: `maybeStartRobotSwell` draws a second seeded chance (`SWELL_COMPANY_CHANCE`) only after the robot pool's own trigger already succeeded, and only acts on it when the locale actually has a `Company` to pick — with zero companies, company-wide was never really on the table that tick regardless of the roll, so it falls straight through to the single-robot path (`startSingleRobotSwell`) instead of aborting.

`startCompanyWideSwell` picks one `Company` and one `SwellRobotAttributeId` via seeded draws (both unfiltered — eligibility is applied per-member next), filters `company.robotIds` down to members passing the same structural-eligibility check the single-robot path uses, and — if that leaves zero eligible members — starts no swell at all this tick: not a re-roll, not a fallback to a different company/attribute or to the single-robot path. Direction and the rising/falling measure counts are drawn **once** and shared lock-step across every member; magnitude stays per-robot, via `robotPeakDeltaForDirection` (the same dispatcher the single-robot path uses — the magnitude half of `pickSwellPeakDelta`/detune's capped variant, given an already-decided direction so a shared, externally-decided one can be reused instead of each member re-deriving its own from its own current value). Because duration is shared but each member's own distance-to-travel differs, a member with less room simply interpolates at a smaller total distance over the same shared window — no separate "rate" concept exists. A company-wide swell is one `ActiveSwell` object stored under one Map key per member (`robotSwellKey(robotId, attribute)`) and counts as **exactly one** swell against the robot pool's 5-cap, regardless of company size.

### Lifecycle and determinism

```typescript
startAudioSwells(localeId: string): void   // idempotent — schedules a 16n repeat via BeatClock's scheduleRepeat
stopAudioSwells(): void                    // idempotent — cancels the schedule AND clears every in-flight swell
tickAudioSwells(localeId: string, measure: number): void  // pure w.r.t. `measure` — testable without a real transport
```

Ticked at **16n resolution** (`scheduleRepeat('16n', ...)`, `getCurrentMeasurePrecise()`), not once per measure — a swell's ramp updates up to 16 times per measure, not in single steps at each measure boundary. `measure` inside `tickAudioSwells` may be fractional (sub-measure precision); `advanceActiveSwells` interpolates from it directly, so `elapsed / totalPhaseMeasures` is a smooth, continuously-advancing fraction rather than a coarse per-measure step. Trigger/selection now rolls on **every tick**, not once per whole measure (docs/specs/AUTOMATION_FREQUENCY_DURATION_SPLIT.md §1.3, superseding this section's earlier once-per-measure gate) — see "Three master controls" below for how the Frequency slider's own rate replaces the old fixed per-measure chance.

Wired into `worldTransition.ts`'s `initializeLocale`, alongside the existing `stopRobotLifecycle()`/`startRobotLifecycle()` pair — `stopAudioSwells(); startAudioSwells(localeId);`, in that order, on every locale (re-)initialization. `stopAudioSwells`'s clear means no swell from a prior locale survives a locale switch or a power cycle (BeatClock silently drops every `scheduleRepeat` registration whenever `AudioEngine.killAll()` runs, same as the robot-lifecycle tick).

Runtime state (`activeSwells`, a plain `Map<string, ActiveSwell>`) lives at module scope in `audioSwells.ts`, never in Zustand — only each tick's resulting field value reaches the store, via the normal `apply*`/`setGlobalAudio` call, same as any other edit (CLAUDE.md: runtime-only state stays out of state). `getActiveSwellSnapshot(pool)` is a small read-only, deduplicated-by-object-identity accessor for tests/future debug UI; nothing else reads `activeSwells` directly.

**Three master controls — Intensity, Frequency, Duration (Fleet Params > Pacing).** Originally one slider (`audioStore.pingVarianceAutomation`, replacing an earlier boolean `audioSwellsEnabled` toggle — `docs/specs/PING-VARIANCE-AUTOMATION.md`) did double duty as both the system's on/off switch and its magnitude dial. `docs/specs/AUTOMATION_FREQUENCY_DURATION_SPLIT.md` split that into three: **Intensity** keeps `pingVarianceAutomation`'s name and magnitude-scaling role but can no longer reach `0`; **Frequency** (`audioStore.swellFrequency`, new) took over the on/off role and replaced the old fixed per-measure trigger chance with a real rate; **Duration** (`audioStore.swellDuration`, new) is the swell-length control described above. All three render as a 2x2 layout in `FleetParamsContent.tsx`'s Pacing group — Tempo+Frequency in one row, Duration+Intensity in the other — not inside any accordion, since they're Rig-wide meta-settings, not per-effect params.

- **Intensity** — `PING_VARIANCE_AUTOMATION_SCHEMA` (`SliderLinear`, `data/audioRigConfig.ts` — lore label "PING VARIANCE AUTOMATION", human label "Automatic Effects"). Displays `[1, 100]%` (raised from `[0, 100]%` — it can no longer double as an off switch); the store's fraction converts at the component boundary with the same `* 100` / `/ 100` pattern the Drift sliders already use. **Magnitude scaling.** Every newly-created swell's `peakDelta` — global, single-robot, or per company member — is multiplied by the Intensity fraction via `scaleSwellPeakByAutomation`, as the literal *last* step of that swell's peak calculation, after direction is picked and after every attribute-specific clamp (`clampVolumeDownward`, the detune cap, the HPF/LPF ceilings). Safe by construction: multiplying an already-clamped delta by a fraction in `(0, 1]` only ever shrinks it toward the current value. Fixed at creation — moving the slider afterward never retroactively rescales an in-flight swell. Intensity has **no on/off role at all** now — that's Frequency's job.
- **Frequency** — `SWELL_FREQUENCY_SCHEMA` (`SliderLog`, `[0, 24]` swells/measure — lore label "PING RECURRENCE", human label "Frequency"), with a custom `formatValue` (`formatSwellFrequency`) so the readout reads "Off" at `0`, "N/measure" at or above `1`, and "every N measures" (the reciprocal) below `1`. `frequencyToPerTickChance(frequency)` (`= frequency / 16`, clamped to `1`) converts the slider's "swells per measure" value into a per-tick trigger probability — `tickAudioSwells` rolls this check on **every** 16n tick now (not once per whole measure), so the long-run rate matches "swells per measure" without needing the old once-per-measure gate. Values above `16` are clamped to the same `1.0` per-tick chance as exactly `16` — "24 times a measure" and "16 times a measure" are behaviorally identical, an accepted ceiling. **Trigger gate.** `tickAudioSwells` reads `swellFrequency` once per tick and only calls `maybeStartGlobalSwell`/`maybeStartRobotSwell` when it's `> 0`.
- **Duration** — `SWELL_DURATION_SCHEMA` (`SliderLinear`, `[1, 24]` measures — lore label "PING SUSTAIN", human label "Duration"). See "Direction, magnitude, and duration" above for `pickSwellSplit`.

**0 (Frequency) is a full stop, not a zero-magnitude swell.** At exactly `0`, no new swell starts, and every swell still in its *rising* phase is forced into an early return — `maybeForceGlobalSwellReturn`/`maybeForceRobotSwellReturn`, called at the top of `advanceGlobalSwell`/`advanceRobotSwell` each tick and now keyed on `frequency` (re-keyed from `automation`/Intensity in `AUTOMATION_FREQUENCY_DURATION_SPLIT.md` §1.3), convert the swell in place (new `peakDelta` from its current live value, `risingMeasures` reset to `0`, `startMeasure` reset to now, `phase` flipped to `'falling'`) so it rides its own already-drawn `fallingMeasures` back to base through the *same* falling-phase interpolation formula every normal completion already uses — no new curve, no new snap-timing concept. No new `ActiveSwell`/`SwellMember` field was needed to mark "already forced": flipping `phase` to `'falling'` is itself sufficient, since the guard is `phase === 'rising'` — a swell already falling (naturally, or because it was forced on an earlier tick) is left untouched, and there is no code path that ever flips a `'falling'` swell back to `'rising'`, so a forced return always rides to completion even if Frequency moves off `0` again before it finishes.

**All three seed once per session, then carry forward — not reseeded on every Attenuation Style switch.** Unlike `eq3.low` and every other per-field seeded value in `globalAudio` (the Reverb, Delay, Chorus and shifter `wet` values are not among them any more: all four are Returns fixed at `1`, see Signal Graph), `pingVarianceAutomation`/`swellFrequency`/`swellDuration` belong with `compressorBeforeDelay` in the carry-forward group: `regenerateGlobalAudioFromSeed` seeds Intensity via `generatePingVarianceAutomation` (`utils/globalAudioSeed.ts` — `getSeededVal` into `[0.10, 0.60]`, narrowed from `[0.33, 0.66]` now that it's magnitude-only) and Frequency/Duration via `generateSwellFrequency`/`generateSwellDuration` (both `getSeededVal` into `[2, 8]`), each only on its own field's first-ever call, tracked by its own `*_UNSEEDED` sentinel (`-1`, outside each field's real domain); every later call — any future Attenuation Style switch or retransmit — leaves the user's current values untouched. `setPingVarianceAutomation`/`setSwellFrequency`/`setSwellDuration` are all plain state writes with no `AudioEngine` call — there's no live node to touch; `audioSwells.ts` simply reads each value fresh on its own next tick.

Every trigger/selection/timing/direction/magnitude decision is a `getSeededVal(noiseMap, dataId, offset, min, max)` draw against the **Attenuation Style** noise map (`getAttenuationStyleNoiseMap`) — `offset` is the current measure (`getCurrentMeasurePrecise()`), monotonic like every measure the beat clock hands out (a wrapped one would replay an identical decision every lap — which is why nothing wraps it). As of docs/specs/AUTOMATION_FREQUENCY_DURATION_SPLIT.md §1.3, this offset is no longer floored to a whole measure first — since trigger/selection now rolls on every 16n tick rather than once per whole measure, a successful tick's target/peak/duration draws key off that tick's own fractional `measure` value directly, so two ticks within the same whole measure (e.g. `3.0` and `3.0625`) draw independently rather than identically. `Math.random()` appears nowhere in `audioSwells.ts`. Two sessions on the same seed still produce an identical swell timeline; a user's own manual edits are the only thing that can make two sessions diverge.

## BPM / Tempo

`audioStore.bpm` — the real `Tone.Transport` tempo, driving every beat-based schedule in the app — is an Attenuation-Style-seeded, live-adjustable value (docs/specs/FREE_SYNC_TOGGLE.md §1.7 moved it off the locale; the original design is docs/specs/archive/BPM_CONTROL.md), not a hardcoded constant. It is the only BPM in the app: the former `locale.settings.bpm` field is gone (docs/DUPLICATE_VALUE_AUDIT.md item 1), and the factory bubble vents that once converted measures to seconds with it now run on plain wall-clock time with no tempo input at all (`BubbleStream.tsx`, docs/BUILDING_DESIGN.md "Bubble Streams"). Nothing decorative reads `audioStore.bpm`.

**Seeded per Attenuation Style, reseeded on a style change only.** `generateAttenuationStyleBpm(attenuationStyleId, attenuationStyleName)` (`src/utils/bpmSeed.ts`) draws one `getSeededVal` sample against that style's own noise map (`getAttenuationStyleNoiseMap` — name-derived, no coordinate dependency) at dataId `'globalAudio.bpm'`, offset `0`, into `BPM_SEED_RANGE` (`[40, 100]`), rounded to the nearest integer. (The dataId is `'globalAudio.bpm'`, not a bare `'bpm'`: the bare key hashes to a spot where simplex noise is nearly flat — measured over 300 styles it gave 9 distinct tempos where this key gives 36 — and `bpmSeed.test.ts` guards the spread.) `audioStore.regenerateBpmFromSeed(attenuationStyleId, attenuationStyleName)` pushes that value through the existing `setBPM` action (state write + `AudioEngine.setBPM`). It is called **first** inside `syncGlobalAudioToCurrentAttenuationStyle` — once at `audioStore.ts` module load, and from the `useAttenuationStyleStore` subscription on every `currentAttenuationStyleId` change — so the `globalAudio` push that follows (a synced Delay resolves against the tempo) already sees the new tempo. A coordinates-only retransmit never changes the Attenuation Style, so it never reaches this: **a hand-dragged tempo survives moving around a world, and is reset by an Attenuation Style switch**, the same as every other Audio Rig edit. This inverts the original design (`docs/specs/archive/BPM_CONTROL.md` §1.3 drew it from the locale's coordinates and reseeded only when those changed); the move exists so a Sync draw can be computed from the style alone — `generateGlobalAudioSettings` and `generateLfoBankSettings` call the same pure `generateAttenuationStyleBpm(id, name)` themselves, with nothing threaded between them. A session or share link carries `bpm`, and `applySessionPayload` applies it after the world rebuild, so a loaded session's own tempo still wins over the reseed. The seeded value is never stored on the Attenuation Style or the `Locale`.

**Tempo drives synced values.** `setBPM` ends with `reapplyTempoSyncedValues` (`audioStore.ts`): every lane that holds a `sync` note re-pushes its resolved Hz (`resolveLaneRateHz`) and a synced Delay re-pushes its resolved seconds (`resolveDelayTimeSeconds`); Free values never move with the tempo. See "Free | Sync" in the LFO section above.

**Live manual override.** The Audio Rig drawer's "Tempo" slider (`BPM_SCHEMA`, `src/data/audioRigConfig.ts` — `[20, 200]`, deliberately wider than the `[40, 100]` seed band on both ends, same "seed narrow, drag wide" convention `PING_VARIANCE_AUTOMATION_SCHEMA` established) binds directly to `audioStore.bpm`/`setBPM`, no unit conversion — unlike Ping Variance Automation's fraction-to-percent split, `bpm` is already stored in the same units the slider displays.

**Instant, not ramped.** `AudioEngine.setBPM` assigns `transport.bpm.value` directly — no `rampTo`. An earlier version ramped it (mirroring `updateRobotMasterVolume`'s `Tone.Gain` ramp), but BPM isn't a continuously-summed audio signal like Gain — an instant tempo change doesn't click, it only affects when future notes get scheduled. Ramping was actively harmful for the live case: the Tempo slider's `onChange` fires continuously during a drag (Radix's `onValueChange`, not `onValueCommit`), far more often than any short ramp could complete, so each call cancelled the previous still-in-flight ramp and restarted a new one — the tempo never settled for the whole drag gesture, audibly ("wishy-washy", no locatable downbeat). Reverted to the instant assignment every DAW uses for tempo changes.

## Note Resolution Pipeline

`scheduleNote(params)` does more than forward to the transport — these behaviors run on every note:

1. **Velocity.** If `params.velocity` is omitted, velocity is derived via `computeNoteVelocitySeeded(robotId, position, robot)` around the neutral baseline `NOTE_VELOCITY_BASELINE` (`0.8` since Robot Performance, roadmap 50.5 — down from `1`, so the louder multipliers below have 25 % of headroom before the clamp instead of only being able to lift a note the variance first pushed down; about 2 dB fleet-wide, Volume untouched). With a `position` (every note the playback loop schedules) the two draws are `performanceRoll(compositionSeed, 'velocityRoll' | 'velocityVariance', position)` — `alea` over `seed:purpose:position`, uniform and independent across robots and ticks, a pure function of its inputs so a replay from power-on repeats it. The robot's **Dynamics** (`Robot.dynamics`, 0–100, absent or NaN = `DYNAMICS_NEUTRAL` 50) scales both the rate and the width: `rate = VELOCITY_VARIANCE_RATE · dynamics / 50` (0.15 at 50, at most 0.3) and `width = VELOCITY_VARIANCE_AMOUNT · dynamics / 50` (± 0.25 at 50, ± 0.5 at 100, flat at 0). Without a `position` (tests, callers outside the loop) the legacy per-robot counter samples the locale noise map at `VELOCITY_ROLL_X` / `VELOCITY_VARIANCE_X` (mod `VELOCITY_PERIOD`, 97) as it always did. Either way the noise map's presence gates the roll (no active locale, baseline only). Result is always clamped to `[VELOCITY_MIN, 1]` (floor `0.05`). This is deliberately independent of `robot.masterVolume` (Roadmap Phase 9) — overall robot loudness moved off per-note velocity entirely and onto each robot's own live bus gain (see `reserveVoice`'s `masterVolume` parameter and `updateRobotMasterVolume`, in "Layered / Composite Voices" above), so a live Volume edit affects an already-sounding note's tail too, not just the next note — something baking the value into per-note velocity could never do, since a struck note's velocity is fixed the instant it triggers.
2. **Motif-group accent and articulation marks.** If `params.accentMultiplier` is set, the velocity resolved in step 1 (or the caller-supplied `params.velocity`) is multiplied by it and clamped back to `[0, 1]`. `processMelodyStep` passes the product of two factors, or `undefined` when that product is exactly 1: the motif-group accent `GROUP_ACCENT_MULTIPLIER` (`1.25`) and the event's **articulation mark** velocity (`resolveArticulation(event).velocity` from `ARTICULATION_MARKS`, `src/engine/articulation.ts`: accent 1.25, marcato 1.4, tenuto 1.1, the staccati 1). The group accent applies to exactly one event per motif-tiling repeat window — whichever of a robot's events has the earliest `startStep` within that window — computed once at `registerRobotMelody()` time (not per-tick) by grouping the melody's `startStep`s by `Math.floor((startStep - 1) / rhythmicMotifLength.value)`. Only applies when the robot's `rhythmicMotifLength.active` is `true`; scatter mode (`active: false`) has no repeat windows, so no event is ever accented. See [MELODY_SYSTEM.md](MELODY_SYSTEM.md) for the motif-tiling model this accents.
   **Rests and marks shorten the note before it gets here.** `processMelodyStep` resolves each event's `rest` / `mark` stamps (MELODY_SYSTEM.md, "Performance Marks") to a sounding-length factor: an unstamped event passes its `NoteDuration` string exactly as before; a shortened one becomes **seconds at the live tempo** — `Tone.Time(event.length).toSeconds() · factor`, floored at `MIN_SOUNDING_SECONDS` (0.03 s) so a staccatissimo never collapses to a click, and never longer than the note as written. A seconds duration reaches the composite voice as its string (Tone reads `"0.075"` as seconds) and `scheduleVoiceRelease` as the number.
   **Humanize** (`audioStore.humanize`, 0–20 ms, pushed in by `AudioEngine.setHumanize(ms)` — engine state, never a store read on the tick) moves each note off the grid by `(performanceRoll(compositionSeed, 'humanize', position) · 2 − 1) · ms / 1000` seconds, added to `time + MIN_LEAD`. `humanizeOffsetFor(position)` is built once per `processMelodyStep` call (the roster read once, nothing at 0 ms) and the draw is independent per robot and tick, so a unison smears rather than shifting together. `MIN_LEAD − HUMANIZE_MAX_MS / 1000` leaves 80 ms, inside CLAUDE.md's 50–100 ms rule. No test checks that sum, so recheck it whenever either constant changes. **Click-track entries are exempt**: `registerRobotMelody` flags the substituted click-track entries and the loop adds no offset to them, since a humanized tempo reference is no reference. Dynamics, Rests, Accents and Humanize are pure trigger-time arithmetic and melody data: the phase added zero audio nodes.
3. **`audioMode` policy** (read fresh from the store each call, not cached): `scheduleNote` itself applies only the `highlight` half — if any robot in the locale is `highlight`, non-highlighted robots have velocity multiplied by `0.5` (~-6dB). `mute`/`solo` enforcement (`mute` drops the note; if any robot is `solo`, every non-solo robot is suppressed) happens downstream in `triggerWithCap`, which every `scheduleNote` call funnels into — the sole enforcement point for mute/solo, not a backup check for a caller that bypasses `scheduleNote`.
4. **Panning.** Every reserved voice's pan is recomputed once per `16n` playback tick (not per note) via `calculatePanFromPosition(x) = (x / WORLD_WIDTH) - 0.5`, giving a range of `[-0.5, +0.5]` (intentionally narrower than full stereo width, to keep the mix centered). `x` comes from the robot's **live GSAP-animated transform** (`getRef('robot-' + robotId)`), falling back to the robot's stored `position.x` if the ref/transform isn't available. That is **Auto**, the default (`Robot.panAuto === true`), and it is unchanged: the write is skipped when the pan moved less than `PAN_WRITE_EPSILON`, and each write is also published to `robotPanReadoutStore` (`useRobotPanReadoutStore`, `src/stores/robotPanReadoutStore.ts`) so the robot screen's Pan slider can show it as a read-only readout. With Auto off (`panAuto === false`) the robot's own `Robot.pan` (full `[-1, +1]`, wider than Auto's range) is written instead: `AudioEngine.updateRobotPan(robotId, value)` pins the panner there, adds the robot to the module-level `manualPanByRobot` map that `updateAllPanners` skips before its DOM read, and ramps over `PAN_RAMP_SECONDS` (0.05 s) so a slider drag or a switch either way never clicks; `updateRobotPan(robotId, null)` hands the robot back to the tick, ramping to wherever it is now. `AudioEngine.getLivePan(robotId)` returns the last Auto value (what Auto-off freezes into `pan`), or `undefined` before the first write, while manual, and after `releaseVoice`, which also clears `manualPanByRobot` and the readout entry. Because release forgets the engine's side, every reservation path (`loadInstruments`' post-load pass, `reRegisterAllRobotsAudio`, `reReserveVoice`) re-primes a manual robot from the store; the store is the source of truth. Auto off stops only the panner following the robot: the robot keeps moving. See [ROBOT_PAN.md](specs/ROBOT_PAN.md).

## Scheduling Patterns

Audio scheduling in Trace Atlas is driven by the transport-backed BeatClock and AudioEngine for sample-accurate, musically-aligned timing.

**Core APIs:**
- `scheduleRepeat()` / `cancelSchedule()` — named exports from `beatClock.ts` (not a `BeatClock.` namespace) — app-facing recurring musical work
- `AudioEngine.scheduleNote()` - note playback entry point
- `Transport.scheduleOnce()` / `scheduleRepeat()` remain engine internals; app code should generally avoid calling them directly

**Lookahead:** Apply the shared `MIN_LEAD` scheduling lead so Web Audio can prepare synths before the attack; the implementation defaults to `0.1s` (100ms).

**Critical rule:** When a beat-based callback runs, use the callback time or `AudioEngine.now()` for scheduling. App code should normally stay on the `BeatClock`/`AudioEngine` path rather than reaching for `Tone.Transport` directly.

**Key patterns:**
- Use the step registry for O(1) melody lookups rather than iterating over robots each tick
- Keep playback state in AudioEngine and let the transport-driven beat clock drive the shared step scheduler
- Clear previous schedules before HMR re-registration
- Cancel beat-clock schedules with `cancelSchedule()` when they are no longer needed

## Common Patterns

The examples below show the current engine-facing patterns for scheduling, melody registration, and cleanup.

### Schedule a Note

```typescript
import { AudioEngine } from '../engine/AudioEngine';
import { scheduleRepeat, cancelSchedule } from '../engine/beatClock';
import { MIN_LEAD } from '../constants';

// Simple immediate trigger
AudioEngine.scheduleNote({
  robotId: 'robot-123',
  note: 'C4',
  duration: '4n',
  velocity: 0.6,
});

// App-facing recurring scheduling uses BeatClock rather than direct Tone.Transport calls.
const scheduleId = scheduleRepeat('4n', () => {
  AudioEngine.scheduleNote({
    robotId: 'robot-123',
    note: 'E4',
    duration: '8n',
    time: AudioEngine.now() + MIN_LEAD,
  });
});

// Later, when the schedule is no longer needed:
cancelSchedule(scheduleId);
```

### Register Robot Melody

```typescript
import { AudioEngine } from '../engine/AudioEngine';
import { generateMelodyForRobot } from '../engine/melodyGenerator';

function setupRobotAudio(robot: Robot): void {
  // Generate and register melody
  robot.melody = generateMelodyForRobot({
    onsetCount: 6,
    octaveMin: 2,

}

function cleanupRobotAudio(robotId: string): void {
  AudioEngine.unregisterRobotMelody(robotId);
}
```

## Forbidden Patterns

The main anti-patterns to avoid are:

1. Creating synths or importing Tone directly outside `src/engine/`.
2. Using `setTimeout`/`setInterval`/`requestAnimationFrame` for music timing.
3. Triggering audio from GSAP timelines or React effects instead of semantic events.
4. Storing synth instances or other non-serializable audio objects in Zustand or component state.

When in doubt, route the behavior through `AudioEngine` and keep the data serializable.

## Audit Checklist

Before committing audio code:

- [ ] No `new Tone.` or `import * as Tone` outside `src/engine/`
- [ ] No timers are used for audio timing
- [ ] No synths or timelines are kept in state
- [ ] All scheduling uses BeatClock/Transport
- [ ] Melodies store indices, not pitch strings

## Lifecycle Summary

Each robot follows a compact lifecycle:

1. **Spawn**: persist `audioAttributes.layers`, then reserve a composite voice for the robot.
2. **Register**: register the melody with `AudioEngine`.
3. **Update**: change layer parameters through `AudioEngine.updateVoiceLayerParams()` or `AudioEngine.reReserveVoice()`.
4. **Cleanup**: unregister the melody and release the voice when the robot is removed.

## Quick Troubleshooting

- If audio does not start, verify that `AudioEngine.start()` was triggered by a user gesture and that `Tone.context.state` is `'running'`.
- If notes drift, use the beat-based scheduler and pass the scheduled time or `AudioEngine.now() + MIN_LEAD` into `AudioEngine.scheduleNote()`.
- If playback becomes crackly, keep polyphony capped in `AudioEngine`; do not add ad hoc voice counters in components or utilities.
- If schedules multiply on hot reload, cancel them with `cancelSchedule()` before re-registering.

### Tone patch: the per-note oscillator leak

Tone 15.1.22's `Oscillator._start` connects the Oscillator's persistent `frequency` and `detune` Signals into a fresh one-shot `ToneOscillatorNode` on every start from the stopped state, and nothing disconnects them when the note ends; standardized-audio-context keeps each connection into an AudioParam in the source's output Set, so every note left one native `OscillatorNode` alive for the life of the page (about two a second on D1 at Light; found by backlog 27's desktop step 1, [todo/scratchy-audio-phones.md](todo/scratchy-audio-phones.md#backlog-27-desktop-step-1--d1-against-d5-at-light-and-what-grows-2026-10-23)).

`src/engine/tonePatches.ts` exports `patchOscillatorEndedDisconnect(prototype)`, which wraps `prototype._start` so the new node's `onended` first calls `frequency.disconnect(node.frequency)` and `detune.disconnect(node.detune)`, inside one `try`, and then runs the handler Tone installed (which disposes the node). It imports no Tone; `src/engine/audioContextSetup.ts`, `main.tsx`'s first app import and so the one module that runs before any Oscillator can start, applies it once at boot to `Tone.Oscillator?.prototype` and exports the result as `oscillatorLeakPatched`. A marker symbol on the prototype makes a second call a no-op. On a Tone that renames the private `_start` (or drops `Oscillator`), the call returns `false` with one `devWarn` and the boot carries on: the leak comes back, nothing breaks. A renamed `_oscillator` leaves the wrapper installing nothing, silently, which `oscillatorLeakPatched` cannot see; a Tone upgrade re-runs the proof run (`npm run perf:audio` on D1 at Light, the by-type `Oscillator` line) rather than trusting the flag.

**Upstream has fixed it, from Tone 15.3.11** ([Tone.js #1379](https://github.com/Tonejs/Tone.js/issues/1379), fixed by [#1393](https://github.com/Tonejs/Tone.js/pull/1393), 2025-12-14: `_start`'s `onended` calls a new `_cleanUpConnections` with the same two disconnects). That release line is on npm's `next` tag; `latest`, which `^15.1.22` and the lockfile resolve to, is still 15.1.22. **On a Tone with the fix, this wrapper is not inert, it throws**: its disconnects run first, then Tone's own cleanup disconnects the same params, and standardized-audio-context throws `Not connected to destination node` out of Tone's `onended`, before Tone's `onstop` and dispose. A scratch repro (one `Tone.Synth`, 120 notes; 2026-10-23) read 120 uncaught errors and 0 of 120 `onstop` calls on 15.5.61 with the wrapper, against none and 120 of 120 without it. So the upgrade to 15.3.11 or later removes `tonePatches.ts` and its call in the same change.
